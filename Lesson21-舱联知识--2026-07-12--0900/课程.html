无线投屏的通信链路——手机画面是怎么"飞"到车机屏幕上的？

一、先想想这个问题

你坐进车里，手机自动弹出提示"连接车载屏幕"。点一下确认，车机屏幕上立刻出现了你的手机界面——导航地图居中显示，音乐播放器在侧边，来电通知浮在右上角。

你没有插数据线，没有手动连接 Wi-Fi，甚至没有输过蓝牙配对码。

手机和车机之间到底走了几条"无形线"？一个屏幕上的画面，怎么在几毫秒内从手机"飞"到车机上，而且每一次触摸操作还能反向回到手机？

今天的重点：无线投屏的通信协议栈——从手机掏出到画面出现，中间发生了哪五个关键阶段。

二、无线投屏的"五阶段模型"

无线投屏（如无线 CarPlay / Android Auto / HUAWEI HiCar）不是一条"管子"把画面直接传过去。它是五层协议栈的接力协作。

图 1 — 无线投屏通信协议栈

flowchart TB subgraph APP["应用层"] UI["车机 UI 渲染 <br>导航/音乐/电话"] Touch["触摸事件采集 <br>触控坐标→回传手机"] end subgraph MEDIA["媒体流层"] H264["H.264/H.265 视频编码 <br>手机屏幕→压缩视频流"] AAC["AAC 音频编码 <br>手机音频→压缩音频流"] end subgraph IP["IP 网络层"] RTP["RTP/UDP 实时传输 <br>视频+音频实时流"] mDNS["mDNS/DNS-SD <br>服务发现"] end subgraph LINK["链路层"] WFD["Wi-Fi Direct (P2P) <br>点对点高速连接"] BLE["BLE <br>发现&配对&唤醒"] end BLE --> WFD WFD --> mDNS mDNS --> RTP RTP --> H264 RTP --> AAC H264 --> UI AAC --> UI Touch -->|"TCP/IP 回传"| WFD

五脏俱全，缺一不可。下面逐一解释每一层在干什么。

三、五大阶段详解

阶段一：BLE 发现与配对（低功耗"握手"）

角色做什么
车机 BLE 外设持续广播特定 UUID 的服务（如 CarPlay 服务标识）
手机扫描附近的 BLE 广播，识别到车载服务后发起连接
配对流程BLE 配对 → 交换能力信息（是否支持 Wi-Fi 6、支持的分辨率、编解码器列表）

为什么先用 BLE 而不是直接 Wi-Fi？

  • BLE 功耗极低（μA 级），车机熄火后也能一直广播
  • BLE 配对交换的"能力信息"决定后续 Wi-Fi 连接的参数（分辨率、编解码、带宽需求）
  • BLE 负责"敲门"，Wi-Fi 负责"搬东西"，各司其职

阶段二：Wi-Fi Direct 建立（高速"管道"）

BLE 配对完成后，手机和车机进入 Wi-Fi Direct（P2P） 建立流程：

步骤动作
1手机和车机协商谁当 Group Owner（GO）——通常是车机
2GO 开辟一个 Wi-Fi Direct 组，分配 IP 地址（DHCP 服务器）
3另一个设备作为 Client 加入该组
4建立 WPA2/WPA3 加密 连接

Wi-Fi Direct 的"隐性优势"：

  • 不需要无线路由器——手机和车机直接点对点通信，带宽可达 300 Mbps~1.2 Gbps（Wi-Fi 5/6）
  • 时延低至 5~10 ms（同一信道、无路由器转发）
  • 这是为什么无线投屏能流畅播放导航画面，而手机热点投屏会卡顿——热点需要经过路由器，多一跳就多 20~50 ms 时延

阶段三：服务发现（谁提供什么服务）

Wi-Fi Direct 连通后，手机和车机需要"互相认识"——这靠 mDNS（多播 DNS） 和 DNS-SD（DNS 服务发现）：

手机广播："我是 iPhone，我支持 CarPlay 音频流服务 _carplay-audio._tcp"
车机响应："我是车载主机，我支持 CarPlay 显示服务 _carplay-display._tcp"

双方交换以下信息：

  • 支持的分辨率（1920×720、1280×800 等）
  • 支持的编解码器（H.264 Baseline/High、H.265）
  • 支持的帧率（30 fps / 60 fps）
  • 支持的最大比特率（20 Mbps / 50 Mbps）

阶段四：媒体流实时传输（画面"飞"过去）

这是最核心的阶段。手机把屏幕画面通过以下链路传给车机：

flowchart LR Phone["📱 手机 GPU <br>渲染屏幕帧"] --> Encoder["H.264/H.265 <br>编码器"] Encoder --> RTP2["RTP 打包 <br>每个帧→多个包"] RTP2 --> WFD2["Wi-Fi Direct <br>无线传输"] WFD2 --> Decoder["车机解码器 <br>解码→显示"] Decoder --> Display["🖥️ 车机屏幕"]
参数典型值
视频编码H.264 High Profile / H.265
分辨率1920×720（宽屏 CarPlay）
帧率60 fps（导航/音乐），30 fps（视频）
编码比特率15~40 Mbps
编码延迟1~2 帧（约 16~33 ms）
传输协议RTP over UDP（实时，不重传）
音频AAC 256 kbps, 48 kHz, 双声道

关键设计决策：为什么不走 TCP？

RTP over UDP： 画面丢几帧比"等重传"好。导航画面偶尔花一下（UDP 丢包）比等重传卡住 500 ms 安全得多。

阶段五：触控回传（你碰车机，手机响应）

用户触摸车机屏幕时，事件通过单独的 TCP 连接（非 RTP）回传手机：

触摸事件 = (x, y, 压力, 触摸ID, 时间戳)
→ TCP 连接 → 手机 → 手机 OS 将触摸注入到"虚拟车机 App"
→ App 响应 → 渲染新帧 → 编码 → RTP → 车机显示
场景端到端延迟（触摸→显示反馈）
理想条件30~50 ms（人类几乎无感知）
较差的无线环境80~120 ms（仍可接受）

五、三条核心规则

#规则一句话
1无线投屏=BLE敲门→Wi-Fi搬货BLE 负责发现和配对（低功耗），Wi-Fi Direct 负责高速传输（高带宽）。两者分工明确，缺一不可
2画面传输用 RTP/UDP，不用 TCP实时画面宁可偶尔丢帧（UDP 丢包导致短暂花屏）也不等重传（TCP 重传导致卡顿）。导航画面卡 500 ms 比花 50 ms 危险得多
3触控回传是独立的"逆流"TCP通道触摸坐标、压力、时间戳通过 TCP 从车机回传手机，保证可靠性（触控不能丢）。视觉流走 UDP，触控流走 TCP——同一 Wi-Fi Direct 链路上的"两条河"
