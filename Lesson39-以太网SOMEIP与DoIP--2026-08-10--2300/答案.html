Lesson 39 — 答案

SOME/IP 与 DoIP——车载以太网上的"服务"是怎么被找到和调用的？— 参考答案

费曼简答题参考答案

Q1（用"点外卖"类比 SOME/IP-SD 服务发现，并解释 TTL 续租）

参考答案方向（点外卖类比）：

报文点外卖类比技术含义
FindService你打开美团，搜索"附近有哪些餐厅"客户端广播："谁提供空调服务？"（带服务 ID）
OfferService餐厅在平台上亮出招牌、地址、营业时间服务端回应："我提供！这是我的 IP + 端口 + 服务 ID"
SubscribeEventgroup你关注了这家餐厅的公众号客户端订阅事件组，之后服务端有新状态自动推送

为什么要周期性重发 OfferService（TTL 续租）？

  • 网络是动态的：ECU 会重启、会休眠唤醒、服务会下线
  • OfferService 报文带一个有效期（TTL），客户端收到后"记住了"这个服务
  • 服务端周期重发 Offer（默认几秒一次）＝"我还活着、我还提供服务"
  • 客户端如果长时间收不到续租 → 认为服务下线，不再调用它——避免调用一个不存在/已失效的服务

一句话： TTL 续租就是"心跳"——服务端定期刷存在感，客户端据此判断服务是否可用。这和 Lesson 10 里 MQTT 的 Keep Alive 是同一个思路。

Q2（Method 和 Event 的区别？各自适合什么场景？）

参考答案方向：

对比Method（方法）Event（事件）
通信方式请求-响应（你问我答）订阅-推送（我主动报）
触发时机客户端需要时才发起服务端状态变化时自动推送
典型场景一次性动作指令持续变化的状态量
车载例子中控发"座椅加热开到 3 档"、"打开天窗"BMS 推送"电量从 80% 变 79%"、车速变化

为什么 Event 能减少网络流量？

  1. 变化才发：传统 CAN 是周期发送（不管变没变都发）；Event 只在状态变化时推送，没变化就不占网络
  2. 订阅才推：客户端订阅了才推送，没订阅的节点收不到——避免广播轰炸全网
  3. 一次推送，多方共享：同一个 Event 可被多个订阅者共享，而 Method 每次调用都要一问一答

一句话： Method 适合"一次性动作指令"（开、关、设置），Event 适合"持续变化的状态"（温度、车速、电量）——Event 按需推送，天然省流量。

Q3（为什么"信号通信 → 服务通信"是软件定义汽车的必经之路？DoIP 的角色？）

参考答案方向：

为什么必须服务化：

角度CAN 信号通信SOME/IP 服务通信
迭代速度改功能 = 改报文矩阵、重新标定、全车联调（以月计）服务独立封装，OTA 只更新相关软件（以天计）
扩展性加功能要动全网配置，牵一发动全身加新服务即插即用，不影响其他节点
动态组合静态绑定，组合困难运行时发现、按需调用（如"语音开空调"组合两个服务）

软件定义汽车的本质 = 功能由软件动态组合，而不是出厂焊死。 SOME/IP 的服务发现（SD）让 ECU 之间"临时组队"，正是软件定义汽车通信层的地基。

DoIP 的角色（结合 OTA）：

  • 带宽：一个整车固件几百 MB ~ 几个 GB，CAN 只有几 Mbps，刷不动；DoIP 走以太网 100/1000 Mbps，快几十上百倍
  • 安全：路由激活（Routing Activation）校验诊断仪权限，VIN 识别保证请求路由到正确的车、正确的 ECU
  • 结论：没有 DoIP，就没有今天的整车 OTA 刷写能力

一句话： SOME/IP 让软件"说得上话、找得到服务"，DoIP 让软件"送得进门、刷得动固件"——两者是软件定义汽车时代通信层的"两条腿"。

选择题答案

MCQ 1：关于 SOME/IP 的四种服务元素，下列说法正确的是？

正确答案：C. Field 是可以读取和修改的属性（getter/setter）

选项分析
A. Method 是服务端主动推送数据的机制❌ 说反了：Method 是"你问我答"的请求-响应；服务端主动推送数据的是 Event
B. Event 是"你问我答"的请求-响应机制❌ 说反了：Event 是订阅-推送，不是请求-响应
C. Field 是可以读取和修改的属性✅ Field（字段）就是"可读可写的属性"——getter 读、setter 写、notifier 通知变化，比如"当前温度""目标温度"
D. Eventgroup 是 Method 的另一种叫法❌ Eventgroup 是事件组——一组相关事件的打包订阅单位，不是 Method 的别称

MCQ 2：服务端启动后主动宣告"我提供某某服务"的报文是？

正确答案：C. OfferService

选项分析
A. FindService❌ FindService 是客户端发的（"谁提供服务？"），不是服务端
B. SubscribeEventgroup❌ SubscribeEventgroup 是客户端发的订阅请求
C. OfferService✅ OfferService 是服务端启动后（或收到 Find 后）主动宣告"我提供某某服务"，带 IP、端口、服务 ID 和 TTL
D. SubscribeAck❌ SubscribeAck 是服务端回应订阅成功的确认报文，不是宣告服务

MCQ 3：相比传统 UDS over CAN，DoIP 最本质的优势是？

正确答案：B. 把 UDS 封装进 TCP/IP 跑在以太网上，速度快几十上百倍，支撑 OTA 大数据刷写

选项分析
A. 不需要建立连接，即发即收❌ DoIP 恰恰需要先建立 TCP 连接（端口 13400），不是即发即收
B. 把 UDS 封装进 TCP/IP，速度快，支撑 OTA✅ DoIP = UDS 报文封装进 TCP/IP，跑在以太网上，带宽从几 Mbps 提到 100/1000 Mbps——OTA 刷写、大数据诊断的前提
C. 不需要 VIN 识别和权限校验❌ DoIP 必须做 VIN 识别和路由激活——这正是它的安全设计
D. 只能用于产线，售后不能用❌ DoIP 在产线（EOL）、售后（远程诊断）、OTA 都能用，不止产线
