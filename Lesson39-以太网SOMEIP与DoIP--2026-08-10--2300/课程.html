SOME/IP 与 DoIP——车载以太网上的"服务"是怎么被找到和调用的？

← 上一课 ☰ 目录 下一课 →

一、先想想这个场景

你想在美团上点一份外卖：打开 App，它自动列出附近所有餐厅，你挑一家、下单、等餐送到。

问题来了： App 是怎么知道"附近有哪些餐厅、它们卖什么"的？餐厅可没有提前把菜单写进你的手机里——是"发现"出来的。

车里也在发生同样的事： 中控想调用"打开空调"这个功能，它怎么知道空调控制器（HVAC ECU）在哪、提供什么服务、怎么连上它？这就是这一课的主角——SOME/IP（Scalable service-Oriented MiddlewarE over IP）。

这一课讲清楚：SOME/IP 是什么、服务是怎么被"发现"的（SOME/IP-SD）、以及 DoIP 如何把诊断"搬"上以太网。

二、从"信号"到"服务"：为什么需要 SOME/IP？

老一代汽车（CAN 时代）的通信方式是"信号"：每个 ECU 的每条报文，ID、长度、发送周期、含义，出厂前就定死了。加一个新功能？改报文矩阵、重新标定、重新测试——非常痛苦。

智能汽车时代，软件要持续迭代（OTA），功能要动态组合（比如"语音开空调"要同时调语音识别、车身控制两个服务）。于是通信方式从"信号"升级为"服务"：

对比维度CAN 信号通信SOME/IP 服务通信
通信对象固定 ID 的报文（信号）服务（方法/事件/字段）
关系建立出厂静态配置运行时动态发现
调用方式周期发送，收不收都发按需请求-响应 / 订阅-推送
扩展性加功能要改网络矩阵加服务即插即用
承载网络CAN / CAN-FD车载以太网（100BASE-T1）

ID=0x123 周期 10ms"] C2["ECU-B 收报文
解析字节 3 得车速"] C1 -- "不管对方要不要，都发" --> C2 end subgraph SOMEIP["🌐 SOME/IP 时代：服务"] S1["中控（客户端）"] S2["空调控制器（服务端）"] S1 -- "请求：把温度调到 22℃" --> S2 S2 -- "响应：已执行 ✅" --> S1 end

一句话： CAN 是"对讲机喊话"（固定频道、定时喊），SOME/IP 是"打电话叫服务"（拨号、接通、对话、挂断）。

三、SOME/IP 的服务接口：四种"能力"

SOME/IP 把 ECU 提供的功能抽象成服务（Service），一个服务包含四种元素：

元素英文类比通信方式
方法Method"打电话问一件事"请求-响应（Request/Response）
事件Event"订阅公众号，有更新自动推给你"服务端主动推送（Publish）
字段Field"一个可以读、可以改的属性"getter / setter / notifier
事件组Eventgroup"一组相关推送的打包订阅"订阅（Subscribe）的最小单位

举个空调的例子：

  • Method：中控发"设置温度 22℃" → 空调控制器响应"OK"（一问一答）
  • Event：中控订阅"温度变化"事件 → 温度一变，空调控制器主动推送新温度（不用中控反复问）
  • Field：中控读"当前温度"（getter）、写"目标温度"（setter）
  • Eventgroup：把"温度、风速、模式"三个事件打包成一个组，一次订阅全收到

关键： Method 是"你问我答"，Event 是"我主动报"，Field 是"可读可写的属性"——这是区分三种元素的口诀。

四、SOME/IP-SD：服务是怎么被"发现"的？

服务不是出厂写死的，而是运行时动态发现的。负责这件事的协议叫 SOME/IP-SD（Service Discovery，服务发现），它靠三种报文完成"牵线搭桥"：

报文谁发干什么
FindService（查找服务）客户端广播："谁提供空调服务？"
OfferService（提供服务）服务端单播/组播回答："我提供！地址是……"
SubscribeEventgroup（订阅事件组）客户端"我要订阅这个事件组"

完整流程：

sequenceDiagram participant C as 📱 客户端（中控） participant S as 🧊 服务端（空调控制器） Note over C,S: 第一步：发现（Discovery） C->>S: FindService：谁提供空调服务？（广播） S-->>C: OfferService：我提供！IP+端口+服务ID Note over C,S: 第二步：订阅（Subscribe） C->>S: SubscribeEventgroup：订阅温度/风速/模式 S-->>C: SubscribeAck：订阅成功 Note over C,S: 第三步：使用（Interaction） C->>S: Method 请求：设置温度 22℃ S-->>C: Method 响应：已执行 S-->>C: Event 推送：温度变为 22℃

两个重要细节：

  1. TTL 续租（保活）：OfferService 报文带一个"有效期"（TTL）。服务端周期性重发 Offer（默认几秒一次），客户端收到就刷新记录；如果长时间收不到 → 认为服务下线了。这就是"心跳"机制。
  2. 可选 vs 必选服务：有些服务（如灯光）是启动就提供的，不用等 Find 才回应；有些是按需启动的——收到 FindService 才起来，省电。

一句话： SOME/IP-SD 就是服务的"红娘"——Find 是"征婚启事"，Offer 是"自我介绍"，Subscribe 是"确定关系"。

五、DoIP：把诊断"搬"上以太网

诊断大家不陌生（Lesson 25 的 UDS）。传统诊断走 UDS over CAN，速度慢（CAN 最快也就几 Mbps）、一次刷写要等很久。DoIP（Diagnostic over IP） 把 UDS 诊断报文封装进 TCP/IP，跑在车载以太网上：

对比UDS over CANUDS over DoIP
传输CAN 总线TCP/IP（以太网）
速度最高 ~8 Mbps（CAN-FD）100/1000 Mbps
典型用途产线/售后小数据诊断OTA 刷写、大数据诊断
端口无（靠 CAN ID）TCP 13400

DoIP 的典型流程：

flowchart LR T["🛠️ 诊断仪 / OTA 服务器"] -- "TCP 连接（端口 13400）" --> G["🚗 DoIP 网关
（路由激活 + VIN 识别）"] G -- "把 UDS 请求路由到目标 ECU" --> E["🔌 ECU（执行 UDS 服务）"] E -- "UDS 响应原路返回" --> G G -- "封装成 DoIP 响应" --> T

DoIP 的三个关键步骤：

  1. 连接建立：诊断仪与 DoIP 网关建立 TCP 连接（端口 13400）
  2. 路由激活（Routing Activation）：诊断仪"报名"，网关检查它有没有权限（防黑客乱诊断）
  3. VIN 识别 + 路由：诊断仪报上车辆 VIN，网关把 UDS 请求路由到指定 ECU

为什么 OTA 需要 DoIP？ 一个整车固件几个 GB，用 CAN 刷要刷到天荒地老；DoIP 走以太网，速度快几十上百倍——没有 DoIP，就没有今天的整车 OTA。

六、三条要记住的规则

📌 规则一：SOME/IP 是"服务化通信"，靠"发现"而不是"出厂配置"

CAN 时代功能是出厂写死的信号；SOME/IP 时代功能是运行时动态发现的服务（Method/Event/Field/Eventgroup）。加新功能不用改全网配置，即插即用。

📌 规则二：SOME/IP-SD 三句话——Find 找、Offer 应、Subscribe 定

客户端广播 FindService 找服务，服务端回 OfferService 亮明身份（带 TTL 周期续租保活），客户端 SubscribeEventgroup 订阅事件组，然后就可以 Method 调用、Event 收推送了。

📌 规则三：DoIP = UDS 搬上以太网，是 OTA 的"高速公路"

DoIP 用 TCP（端口 13400）承载 UDS 诊断，速度比 CAN 快几十上百倍。路由激活 + VIN 识别保证只有"有权限的人"能诊断——刷写快 + 够安全，缺一不可。
