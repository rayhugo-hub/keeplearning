一、先想想这个场景：一个 9 KB 的突发，凭什么把关键帧推到 720 微秒之后

摄像头 ISP 在极短时间里把 6 帧画面一起交给交换机——对外口来说，这就是一个 9 KB 的突发。出口队列瞬间排满，而转向角、制动指令那一帧，就排在它后面。

100 Mbps 链路上，把 9 KB 发完需要 9000 ÷ 12 500 000 B/s ≈ 720 µs。可关键控制流的端到端时延预算常常只有 250 µs 上下——还没出门就超预算了。

这不奇怪：以太网出口是"先来先走"的，队列里排在你前面的字节，你必须等它走完。所以问题的本质是——突发必须被削平，否则关键帧没有活路。

L47 / L54 学过的 Qbv 门控 能解决，但代价不小：需要 gPTP 全网时钟同步、需要离线算时间表、需要逐跳都支持。工程上很重。

802.1Qav（FQTSS，转发与排队增强） 提供了一条轻量的路子——信用整形（CBS，Credit-Based Shaper）：不需要全局时钟，只给"有带宽承诺"的那几类队列配一个额度斜率，让它们按承诺的速率平均地发，同时只允许很小的突发。

flowchart LR IDLE["😴 队列空闲：信用以 idleSlope 上涨（在攒额度）"] --> ZERO["⚖️ 信用回到 0：有帧在等 → 允许开始发送"] ZERO --> SEND["📉 发送中：信用以 sendSlope 下滑（负斜率）"] SEND --> NEG["🔻 一帧发完：信用为负，禁止开始下一帧"] NEG --> IDLE

上图就是 CBS 的全部灵魂：信用像锯齿一样上下摆动，摆动的节奏决定了这个队列能跑多快。

类比：给每个队列发一张储值卡。卡里没钱（余额为负）不许消费；不消费的时候余额慢慢涨（攒额度）；一消费就按"整口速度"快速扣钱，扣到负数就得停下来等。

二、一个概念：每个队列一张"储值卡"，只准刷余额

CBS 的规则少得惊人——两条斜率 + 一道门槛：

队列状态信用怎么变允许做什么
空闲（没轮到它发）以 idleSlope 上涨（攒额度）信用 ≥ 0 时，一旦轮到它就能开新帧
正在发送以 sendSlope 下降（负数）必须把这一整个帧发完，不能中途停
信用 ≥ 0—准入门槛：只有它 ≥ 0，才允许开始发送一个新帧
信用 < 0—刹车：一个字节都不许发，等它涨回 0

两个关键点：

  • sendSlope 一定是负的：sendSlope = idleSlope − portTransmitRate。因为端口速率（整口带宽）必然大于 idleSlope（那只是给这一类的预留份额）——发送时它按整口速度在花，可"工资"只有 idleSlope，所以余额被快速扣掉，等于还债。
  • 门槛卡在"开始"这一刻，不卡在"发送中"。一旦放行，这一帧必须完整发完——这是以太网的物理约束（前导码 + 数据 + CRC 是不可切分的一个传输单元）。

守恒定律：为什么平均速率恰好等于 idleSlope

设端口速率 R、帧长 L 字节、预留斜率 S（就是 idleSlope）：

阶段耗时信用变化
发送这一帧L / R掉 L × (1 − S / R) 字节
攒回 0L × (R − S) / (R × S)涨回 L × (1 − S / R) 字节
一个完整周期L / S净变化 0

于是：长期平均速率 = L ÷ (L / S) = S = idleSlope。

这就是整形器的"守恒定律"：你预留多少，长期就只能跑多少。既不会超发，也不会被别的类挤掉。

数值感受（100 Mbps 口，idleSlope = 25 Mbps，帧长 1500 字节）

100 Mbps = 12.5 MB/s；25 Mbps = 3.125 MB/s。

  • 发送耗时：1500 ÷ 12.5 MB/s = 120 µs，期间信用从 0 掉到 −1125 字节
  • 攒回 0：1125 ÷ 3.125 MB/s = 360 µs
  • 一个周期：120 + 360 = 480 µs，而 1500 ÷ 3.125 MB/s = 480 µs ✔
  • 长期平均：25 Mbps，与 idleSlope 一分不差

三、"空闲率闲置"的真正含义：idleSlope 是预留，hiCredit 是刹车

idleSlope（空闲斜率）——名字的由来与它的真实身份

名字直译就是"队列空闲时信用上涨的斜率"。但它真正的身份是带宽预留：

  • 信用按时间累积，与该队列有没有流量、别的队列忙不忙都无关。所以哪怕某个类整天不发一帧，它的额度也不会被普通流抢走。
  • 这就是"空闲率闲置"的含义：闲置期照样计息。好处是它保证了流的带宽承诺；代价是——这份额度别人也用不了。
  • 因此所有 SR 类的 idleSlope 之和不能超过端口带宽。经典 AVB 里有个业界常说的 "75% 规则"：单类 idleSlope 通常不超过端口速率的 75%（为最坏干扰留余量），A + B 之和还要更保守。车载上具体数值以 IEEE 802.1DG 的 profile 与整车实测标定为准。
  • 反过来要清醒：预留承诺的是"速率"，不是"实际需求"。idleSlope 配小了 → 流跑不上去（吞吐被整形器压住、队列持续积压、时延攀升、最终溢出丢帧）；配大了 → 白占出口容量，挤掉别的业务。

hiCredit（信用上限）——突发刹车

如果没有上限会怎样？一个空闲了整整一秒的队列会攒下 idleSlope × 1 s 的巨额信用，一有帧到达就连续全速发一大串——这比不整形还糟，因为突发是"攒出来的"，而且它会在最坏的时刻打穿下游缓冲。

  • 标准要求 hiCredit 不小于 idleSlope ×（最大干扰帧的传输时间），工程上就按这个值配。
  • 算一遍：100 Mbps 口、idleSlope 25 Mbps、最大帧（含 VLAN 标签）1542 字节 ≈ 123.36 µs → hiCredit ≈ 25 Mbps × 123.36 µs ≈ 386 字节。
  • 妙处在于：即使刚被一个最大帧挡了 123 µs，攒下的额度也不够"额外多发一帧"——突发被牢牢锁在一个帧之内。

loCredit（信用下限）——保证"开了就必须发完"

发送时信用一路下滑，下限是 loCredit = sendSlope ×（最大帧传输时间）：一个最大帧全速发完最多能掉到哪里。因为"一旦开始就必须发完"，信用最多掉到这里——它保证任何已经开始发送的帧都能完整发出，不会被信用见底丢在半路。

这也顺手点出了 CBS 的边界：它只能管"要不要开始发"，管不了"已经发出的帧"。要打断已在发的帧，得靠 L54 的帧抢占。

四、它和 L47 / L50 / L53 / L54 那些机制怎么配合

机制位置管什么与 CBS 的关系
Qbv 门控（L47）交换机出口队列按全局时间表开关队列——管"什么时候准发"最佳组合：Qbv 只管闸门开合，门一开队列里积压的帧会以线速涌出；CBS 在门口按 idleSlope 限速，把脉冲摊成平缓流。Qbv 管准点与确定性，CBS 管平均速率与有限突发——CBS 给不了硬时延上界
PSFP 入口监管（L53）交换机入口按每流过滤 / 门控 / 限速——管"这帧有没有资格进场"位置互补：入口设卡防"坏流"，出口整形防"突发"，可以同时配
帧抢占（L54）出口 MAC 内部（MAC Merge）让正在发的普通帧给关键帧让路互不替代：CBS 管不了"已在发的帧"（loCredit 正是保证它必须发完）；帧抢占专治这个。两者接续工作：先被 CBS 整形，再在需要时被抢占
FRER（L50）双路径复制 / 去重链路失效不丢帧必须对称配置：去重靠时序窗口判断两副本谁先到；若两条冗余路径上的 CBS 排队时延不一致（比如一侧 idleSlope 配小了），窗口就得放大——等于把冗余换来的时延预算又送掉了
MACsec（L52）/ PHY（L48）加密 / 物理层内容可信 / 比特上线无直接交互，但都吃帧长预算：加密追加的 ICV 让同一帧更长，在 CBS 里"更贵"（发送耗时与信用消耗都增加）

把 L47~L55 串一遍（一帧摄像头数据的旅程）：

flowchart LR IN["入口：PSFP 每流监管<br>有没有资格进场"] --> SW["转发引擎<br>按 VLAN / 流分类入队"] SW --> OUT["出口队列<br>CBS 信用整形 + Qbv 门控"] OUT --> MM["MAC Merge / 帧抢占<br>给关键帧让路"] MM --> LINK["链路 / PHY<br>冗余路径 FRER 双发去重"]

为什么车载里几乎总是"Qbv 门控 + CBS 整形"一起配？ 因为 Qbv 是闸门，不是减速带：

flowchart LR G1["只配 Qbv：开门瞬间"] --> B1["队列里积压一整周期的帧<br>以线速涌出（脉冲突发）"] B1 --> C1["下游缓冲被打满<br>关键帧被挤 / 抖动 / 丢帧"] G2["Qbv + CBS：开门期间按 idleSlope 限速"] --> B2["积压帧被摊平<br>平缓流出（速率有界）"] B2 --> C2["下游缓冲可控<br>时延更可预测"]

五、工程要点

  1. idleSlope 之和 ≤ 端口带宽：把所有 SR 类的预留相加，工程上常控制在端口速率的 75% 以内（经典 AVB 的"75% 规则"），给最坏干扰留余量。
  2. idleSlope 要对齐"流的最大需求"，不是平均需求：配小了流跑不上去，配大了白占带宽。要拿流的真实码率 + 突发去标定。
  3. hiCredit 必须配，不能放任：否则闲久了的队列会攒出巨型突发，把下游一次打穿。
  4. CBS ≠ Qbv：CBS 只承诺"平均速率 + 有限突发"，不提供硬时延上界。需要确定性时延，还得靠 Qbv 的时刻表。
  5. 有门控的队列几乎都该配 CBS：否则开门瞬间就是一次脉冲突发。
  6. 冗余路径的 CBS 必须对称：FRER 两侧配置不一致 → 去重窗口被迫放大 → 吃掉时延预算。
  7. 队列积压不等于丢帧，但积压终会溢出：CBS 只是"延后"，不保证"不丢"。要与 PSFP / 入队监管 / 队列长度管理配合。
  8. 验证要靠计数与抓包：per-queue 的入队 / 出队 / 丢弃计数，以及芯片的 CBS 状态 / 信用诊断计数，是排查"整形到底有没有生效"的第一手证据。

六、三条铁律（记住这三句）

  1. 两条斜率 + 一道门槛：队列空闲时信用按 idleSlope 上涨，发送时按 sendSlope（= idleSlope − 端口速率，负值） 下降；只有信用 ≥ 0 才准开始发新帧，而一旦开始必须发完（loCredit 兜底）。
  2. idleSlope 是预留、hiCredit 是刹车：一个完整周期 = 帧长 / idleSlope，所以长期平均速率 = idleSlope；hiCredit ≈ idleSlope × 最大干扰帧时间（100 M / 25 M / 1500 B 下约 386 字节），把突发锁在一个帧以内。
  3. 它管"平均"不管"准点"：CBS 不给硬时延上界，常与 Qbv 门控组合（开门限速防脉冲突发）、与 PSFP 分工（入口资格 vs 出口速率）、与 帧抢占接续（CBS 管不了已在发的帧）。

七、费曼简答题（用自己的话，不许用术语）

Q1：用"储值卡"打比方：为什么信用要分两种斜率——不发送时慢慢涨、发送时快速掉？为什么必须"余额 ≥ 0 才能开始发，但一旦开始就必须把这一帧发完"？这套规则为什么能让长期平均速率刚好等于 idleSlope？（提示：一帧的"发送耗时 + 攒回信用的耗时"合起来正好是 帧长 ÷ idleSlope；发送时它按整口速度花钱、却只有 idleSlope 的"工资"）

Q2：什么是 idleSlope？为什么说它代表"带宽预留"——队列一直闲着，这份额度也不会被别人抢走？为什么必须给信用设一个上限 hiCredit？如果不设上限，一个空闲了很久的队列会干出什么事？（提示：信用按时间累积、与别的队列无关；闲置期照样计息；长期空闲攒出巨型突发）

Q3（进阶）：CBS（Qav）、Qbv 门控、PSFP 入口监管、帧抢占 四者各在哪个位置、管什么、能不能互相替代？为什么车载里常用"Qbv 门控 + CBS 整形"组合——门一开、队列里积压的帧会以线速冲出去，这对下游意味着什么？CBS 为什么给不了硬时延上界？再想一想：FRER 的双路径为什么要求 CBS 对称配置？（提示：闸门 vs 减速带；CBS 承诺只有"平均速率 + 有限突发"；去重靠时序窗口）
