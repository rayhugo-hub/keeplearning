UDS 统一诊断服务——维修工是怎么"读懂"你的车的？

一、先想想这个场景

你的仪表盘亮起了发动机故障灯（MIL）。你开到 4S 店，维修工拿出一台笔记本大小的诊断仪，往车上的 OBD 接口一插。不到 30 秒，屏幕上显示：

"P0301 — 1 号气缸检测到失火，累计 47 次，最近一次发生在引擎水温 92°C 时。"

维修工敲了几下键盘，又打了几个命令，10 分钟后故障码清掉了，系统自检通过。

问题：诊断仪和你的车之间到底在"说"什么语言？为什么一个通用的插口就能读取所有品牌的汽车的故障？如果诊断仪想"刷写"ECU 的新固件，它和 ECU 之间又该怎么对话？

这就是本节课的核心：UDS（Unified Diagnostic Services，统一诊断服务）——全球汽车 ECU 用来做诊断、配置、刷写的标准"对话协议"。

二、UDS 是什么？

UDS 是 ISO 14229 定义的一套应用层诊断协议。它不是一根线、一个接口，而是规定：

"当诊断仪（Tester）向 ECU 发一个字节 X，ECU 应该回什么字节 Y，以及这串字节对应的物理意义。"

概念说明
协议全称Unified Diagnostic Services (ISO 14229)
通信方式请求-响应模型：Tester（诊断仪）发请求 → ECU（电子控制单元）回响应
传输层可跑在 CAN 上（UDSonCAN，ISO 15765-3）或以太网上（DoIP，ISO 13400）
行业地位全球主流 OEM 统一使用（以前各厂商各有一套私有协议，UDS 将其统一）
用在哪产线终检、4S 店诊断、OBD 年检、OTA 刷写、远程诊断

UDS 定义了 6 大类 26 种服务，每类服务有一个 SID（Service IDentifier，服务标识符）——就是一个 8 位字节。

三、UDS 的"一问一答"通信模型

3.1 消息结构

一条 UDS 消息由以下部分组成（以 UDSonCAN 为例）：

┌──────────┬──────────┬─────────────┐
│ PCI      │ SID      │ Data        │
│ (协议控制) │ (服务ID)  │ (参数/数据)   │
│ 1~3 字节  │ 1 字节   │ 0~4095 字节  │
└──────────┴──────────┴─────────────┘

关键规则：

  • 请求：Tester 发送 SID + 子功能/参数
  • 肯定响应：ECU 回复 (SID + 0x40) + 数据（如请求 0x10，响应 0x50）
  • 否定响应：ECU 回复 0x7F + SID + NRC（如 0x7F 0x10 0x22，表示"条件不正确"）
sequenceDiagram participant T as "🔧 诊断仪 (Tester)" participant E as "⚙️ ECU" Note over T,E: 一条完整的 UDS 对话 T->>E: 📨 请求：0x10 0x03<br>(诊断会话控制 → 扩展会话) E-->>T: ✅ 肯定响应：0x50 0x03 0x00 0x32 0x01 0xF4<br>(进入扩展会话，P2 超时 500ms，P2* 超时 5000ms) T->>E: 📨 请求：0x22 0xF1 0x90<br>(读取 DID F190→ 读取 VIN 码) E-->>T: ✅ 肯定响应：0x62 0xF1 0x90 ...<br>(返回 VIN 号) T->>E: 📨 请求：0x2E 0xF1 0x82 + 数据<br>(写入 DID F182→ 配置参数) E-->>T: ✅ 肯定响应：0x6E 0xF1 0x82<br>(写入成功) T->>E: 📨 请求：0x11 0x01<br>(ECU 复位 → 硬复位) E-->>T: ✅ 肯定响应：0x51 0x01<br>(复位前确认) Note over E: 🔄 ECU 重新启动

3.2 否定响应码（NRC）

当 ECU 无法执行请求时，它不会沉默——而是返回否定响应，并附上一个NRC（Negative Response Code）告诉 Tester 具体原因。

NRC名称含义典型场景
0x10GR一般拒绝不支持该服务
0x11SNS服务不支持请求的 SID 不存在
0x12SNF子功能不支持SID 正确但子功能不存在
0x13IMLF消息长度错误或格式错误少发了参数
0x22CNC条件不正确不在正确的会话模式
0x24RSE请求序列错误需要先做安全访问再写数据
0x31ROOR请求超出范围DID 或数据值超出允许范围
0x33SAD安全访问被拒绝安全访问密钥错误
0x36LNOK上传下载未授权刷写流程中先请求下载

一条完整性规则：

每一个 UDS 请求，ECU 都必须回复——要么是肯定响应，要么是否定响应 + NRC。绝对不能"不回复"。这确保了诊断仪永远不会"悬空"等待。

四、三种诊断会话

UDS 定义了三种标准的诊断会话，"会话"决定了 Tester 可以做什么操作。

"0x10 0x03" .-> EXT EXT -. "0x10 0x02" .-> PROG
会话SID 子功能允许的操作典型场景
Default (0x01)上电默认读取故障码(DTC)、读取 VIN、读取版本号正常行驶、年检 OBD 扫描
Programming (0x02)0x10 0x02刷写固件、上传/下载数据块OTA 升级、4S 店刷写
Extended (0x03)0x10 0x03读写 DID、IO 控制、例程控制配置参数、高级诊断

为什么不能所有操作都在 Default 会话完成？

安全。如果任何人在 Default 模式下就能刷写固件，恶意设备插上 OBD 口就能把刹车控制器的固件改掉——后果不堪设想。层级递进的会话 = 层级递进的权限控制。

五、常见 UDS 服务速查

以下 7 个服务覆盖了 90% 的日常诊断场景：

SID服务名称作用请求示例肯定响应
0x10DiagnosticSessionControl切换会话10 03 → 扩展会话50 03
0x11ECUReset复位 ECU11 01 → 硬复位51 01
0x19ReadDTCInformation读取故障码19 02 → 读当前故障59 02 + 数据
0x14ClearDiagnosticInformation清除故障码14 FF FF FF FF54
0x22ReadDataByIdentifier读取 DID（VIN、版本）22 F1 90 → 读 VIN62 F1 90 + 数据

小技巧： 肯定响应的 SID = 请求 SID + 0x40。知道请求 SID，就能算出响应 SID：

  • 0x10 → 0x50
  • 0x22 → 0x62
  • 0x2E → 0x6E
  • 0x11 → 0x51

六、三条规则总结

1. 一问一答，永不沉默——Tester 发请求（SID + 参数），ECU 必须回复：肯定响应 = SID+0x40 + 数据，否定响应 = 0x7F + SID + NRC

2. 三级会话，逐级授权——Default（只读）→ Programming（刷写）/ Extended（写入），权限逐级提升，切换会话后才能做相应操作

3. 所有操作通过 SID 组织——读数据用 0x22，写数据用 0x2E，读故障用 0x19，清故障用 0x14，复位用 0x11——每个 SID 对应一类操作，整齐划一

UDS 的精髓： 它定义了一套统一的"汽车诊断语言"——不管你是丰田、大众还是比亚迪的 ECU，诊断仪插上 OBD 口，发同一个 SID 就能做同一件事。这是汽车行业从"各自为政"走向"标准统一"的经典范例。
