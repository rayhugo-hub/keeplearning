车载信息安全——HSM、SecOC、Secure Boot 如何守住"车轮上的电脑"？

← 上一课 ☰ 目录 下一课 →

一、先想想这个场景

2015 年，两位安全研究员 Charlie Miller 和 Chris Valasek 做了一件震惊全球的事：他们坐在 10 英里外的沙发上，通过车辆的娱乐系统（Uconnect 车机），一路攻进 CAN 总线，远程控制了一辆正在高速上行驶的 Jeep Cherokee——关掉空调、启动雨刮、切断变速箱，最后让车在高速上熄火停了下来。克莱斯勒因此召回 140 万辆车。

问题来了：

  • 车机（娱乐系统）和刹车、转向之间，为什么能"一竿子捅到底"？
  • 网关不是有防火墙吗？为什么没拦住？
  • 今天的新车都在宣传"信息安全"——它们到底用什么技术来防这类攻击？

答案是三大安全支柱：Secure Boot（可信启动）、HSM（硬件安全模块）、SecOC（安全车载通信）。 这三大技术分别守住"启动关"、"密钥关"和"通信关"。汽车正在从"机械产品"变成"车轮上的数据中心"，信息安全已经从"可选"变成"法规强制"（UN R155/R156）。往下看，这三大支柱分别怎么工作。

二、先搞懂敌人：汽车的攻击面有多大？

黑客要入侵一辆车，总得有个"入口"。现代汽车的攻击面比你想象的大得多：

关键认知： 攻击者不一定直接攻刹车——更常见的路径是"从最软的入口进，横向移动，再打关键 ECU"。所以信息安全的本质不是"堵住一个口"，而是纵深防御（Defense in Depth）：每一层都有独立防护，攻破一层还有下一层。

三、支柱一：Secure Boot——"启动关"，保证跑起来的代码是可信的

为什么需要它？

攻击者可以刷写 ECU 的 Flash，植入恶意固件（比如让刹车 ECU"听黑客的话"）。Secure Boot 要保证：ECU 每次上电，只运行"经过签名验证"的代码。

信任链（Chain of Trust）

flowchart LR ROM["BootROM
(硬件固化，不可改)
含根公钥"] -->|"验证签名"| SBL["一级引导 SBL
(Secondary Bootloader)"] SBL -->|"验证签名"| APP["应用固件
(App Firmware)"] APP -->|"验证签名"| DATA["关键数据/配置
(签名+加密)"]
  1. BootROM：出厂烧死在芯片里，物理上不可修改——它是信任的"根"
  2. 一级引导：BootROM 用根公钥验证 SBL 的签名，通过才执行
  3. 应用固件：SBL 验证 App 固件的签名，通过才跳转
  4. 每一级都验签，任何一级失败 → 拒绝启动（或进入安全恢复模式）

打个比方： 就像机场安检——你进航站楼（BootROM）查一次证件，登机口（SBL）再查一次，上飞机（App）还要对一次座位号。每一道门都验证上一道门给的凭证，整条链才可信。

配套：Secure Debug / Secure Flash

  • 调试口（JTAG/SWD）要认证后才开放，防止攻击者用调试器直接读内存
  • Flash 刷写要签名校验，非授权固件写不进去

四、支柱二：HSM——"密钥关"，把钥匙锁进保险柜

为什么软件加密不够？

密钥如果存在普通 Flash 里，攻击者读出固件就能把密钥一起挖走——加密形同虚设。

HSM 是什么？

HSM（Hardware Security Module，硬件安全模块） 是芯片里的一块独立安全岛：

flowchart LR subgraph HSM["🔒 HSM 安全岛"] CPU["安全 CPU
(独立内核)"] KEY["密钥存储
(不可读出的安全区)"] CRYPTO["硬件加速器
AES/RSA/ECC/SHA"] TRNG["真随机数发生器"] end MCU["主控 MCU
(应用处理器)"] -->|"请求：帮我签名/加密"| CPU CPU -->|"返回：密文/签名结果"| MCU

HSM 的核心特性：

特性说明防什么
密钥不可读密钥存于安全存储区，任何软件（包括主控）都读不出来固件被逆向，密钥挖不走
运算不外出加解密/签名在 HSM 内部完成，密钥不出芯片总线窃听拿不到密钥
独立 CPU即使主控被攻破，HSM 仍在运行攻击者无法利用主控漏洞操作密钥
真随机数硬件 TRNG 生成高质量随机数随机数可预测导致密钥被破解

打个比方： 普通软件加密 = 把钥匙藏在床垫下（黑客翻一翻就找到了）；HSM = 钥匙存在银行保险柜，你只能请柜员（HSM）帮你开门，柜员绝不把钥匙给你。

五、支柱三：SecOC——"通信关"，让总线上的每条消息都"验明正身"

攻击者能对 CAN 总线做什么？

CAN 总线是广播式的——只要物理接上去，任何节点都能伪造报文（比如伪造"刹车指令"）或重放旧报文（把之前录下的合法刹车指令再发一遍）。

SecOC（Secure On-board Communication，安全车载通信）原理

给每条关键报文加"认证标签（MAC）"，接收方验证通过才执行：

sequenceDiagram participant S as 发送 ECU participant R as 接收 ECU Note over S,R: 双方共享密钥 K（存于各自 HSM） S->>S: 报文数据 + 新鲜值(滚动计数器) 拼接 S->>S: 用密钥 K 计算 MAC S->>R: 发送 [数据 + 新鲜值 + MAC] R->>R: 用密钥 K 重新计算 MAC R->>R: 比对 MAC + 检查新鲜值是否单调递增 alt MAC 匹配 且 新鲜值有效 R->>R: ✅ 执行该报文（可信） else MAC 不匹配 或 新鲜值过期 R->>R: ❌ 丢弃报文（防伪造/防重放） end

SecOC 防住的两类攻击

攻击类型攻击方式SecOC 的防御
伪造（Spoofing）伪造一条"刹车指令"报文没有密钥 K，伪造的 MAC 验证失败 → 丢弃
重放（Replay）录下合法报文，稍后重发新鲜值（滚动计数器）必须单调递增，旧值重放 → 丢弃

注意权衡： 每帧报文多了 MAC 和新鲜值字段，带宽开销增加（CAN 帧只有 8 字节数据域）。所以 SecOC 只保护关键报文（制动、转向、动力、解锁等），非安全相关报文不走 SecOC。

完整攻击场景推演（2015 Jeep 式攻击为什么今天很难成功）：

  1. 黑客攻破车机（最软的入口）✅ 仍可能发生
  2. 想横向移动到制动 ECU → 网关防火墙先挡一道
  3. 就算进了网关，想刷恶意固件 → Secure Boot 验签不通过，拒绝启动
  4. 想伪造 CAN 报文 → 没有 HSM 里的密钥，SecOC 验 MAC 失败，报文被丢弃
  5. 想读密钥 → 密钥在 HSM 安全区，物理上读不出来

结论： 单靠任何一项都不够，但四道防线串起来，攻击成本呈指数上升。信息安全的目标从来不是"绝对攻不破"，而是让攻击成本远高于攻击收益。

七、三条要记住的规则

📌 规则一：汽车安全 = 纵深防御，不是单点防护

攻击者永远挑最软的入口（车机、蓝牙、OBD）。所以防护必须分层：边界（网关）→ 启动（Secure Boot）→ 密钥（HSM）→ 通信（SecOC）。攻破一层还有下一层，这才是现代车规安全的正确姿势。

📌 规则二：密钥必须"硬件锁死"，软件加密等于没加密

密钥存在普通 Flash 里，固件被读出来密钥就没了。HSM 的价值在于：密钥物理不可读、运算不外出、独立于主控运行。"安全强度"最终取决于密钥藏在哪。

📌 规则三：SecOC 防的是"伪造 + 重放"，新鲜值（计数器）和 MAC 缺一不可

MAC 保证"这条消息确实是持钥者发的"（防伪造）；单调递增的新鲜值保证"这条消息不是旧消息重放"（防重放）。只验 MAC 不查新鲜值，录下合法报文重放照样能骗过系统。
