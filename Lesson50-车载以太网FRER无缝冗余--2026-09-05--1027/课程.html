一、先想想这个场景

高速上，L3 级自动驾驶正在行驶，方向盘后面没有驾驶员。智驾域控算出"前方有障碍，向右打 5°"，要把这条指令送到转向执行器。就在此刻，连接它们的那根网线——线束被磨损、连接器松脱、或者被老鼠咬断——指令丢了。执行器等不到指令，车直直往前开。

一条线，决定一车人的安全。

网络永远不是 100% 可靠的：线缆会断、连接器会松、电磁干扰会毁帧。对视频流来说，丢几帧无所谓（下一帧马上就来）；但对刹车、转向这种闭环控制指令，丢一条 = 系统在那一瞬间"失聪"。

功能安全（ISO 26262，前面学过）对 ASIL D 系统有一条硬要求：fail-operational——一个部件坏了，系统必须还能继续工作，不能直接趴窝。网络也一样：一条链路断了，指令必须还能送到。怎么办？

这一课讲清楚：FRER（帧复制与消除，IEEE 802.1CB）——把每个关键帧"发两份、走两条路"，接收端"只收一份"。断了一条路，另一条路的副本照样到：不重传、不等待、控制不中断。

二、为什么"丢了再补发"救不了刹车？——事后补救 vs 事前双发

直觉方案："丢了就重发嘛，TCP 不就是这样？" 但算一笔时间账：

步骤耗时说明
① 接收端发现丢了≥ 一个帧周期得等"下一帧该来却没来"才能判断
② 反馈给发送端一个网络来回发"我丢了"的通知
③ 发送端重发又一个网络来回重走一遍网络
④ 接收端收到—全程 ≥ 2~3 个来回

而控制闭环里，转向指令的周期可能只有 1~10 ms——晚 1 ms，车就偏出去一点。等"发现 → 报告 → 重发 → 送达"整条链走完，黄花菜都凉了。而且重传还会加剧网络拥塞。

FRER 的思路完全反过来： 别等丢了再补救——发送时就发两份，走两条互不相干的物理路径。一条路断了，另一份副本早就（或正从好路上）赶来，接收端总能收到一份——切换时间 ≈ 0，这就是"无缝"。

维度丢包后重传（事后补救）FRER 双路齐发（事前冗余）
动手时机丢了之后才发现、才补救发送时就已经复制两份上路
补救延迟≥ 2~3 个网络来回0——另一份副本已经在路上
控制闭环体验等待期间执行器"听不到"指令任意时刻都能收到一份
平时带宽1 份2 份（带宽 ×2）
适用流量诊断、OTA 等非实时数据转向/制动等安全关键控制流

三、FRER 的思路：复制 → 分路 → 消除

FRER 干的事可以概括为三个动作（对应 802.1CB 的三大功能）：

  1. 复制（Replication）：发送端（或入口交换机）把每个关键帧复制成两份，并给两份贴上"我是同一份"的记号，分别送上两条路；
  2. 分路（成员流 Member Stream）：两份副本各自成为一条成员流，走物理上不同的路径（不同线束、不同交换机）；
  3. 消除（Elimination）：接收端（或汇合点）把两份副本只放行先到的一份，后到的重复副本直接丢弃——上层应用看到的始终是"一份不多、一份不少"。

名词作用类比
流（Stream）一路端到端业务，如"转向指令流"一份连续寄出的信
成员流（Member Stream）复制出的每一路副本流同一封信的两条邮路副本
复制功能（Replication）入口处每帧复制成多份、打记号、分路发送誊写两份、编同一个号
消除功能（Elimination）汇合处/接收端只放行先到的一份收件人只读一份就够
恢复功能（Recovery，可选）把乱序/时延差纠正回原样把信按原顺序整理好
一句话：复制让"两条路都有一份"，消除让"应用只看到一份"——这就是"双路齐发、只收一份"。

四、怎么认出"同一份"？——R-TAG 与序号

两份副本凭什么证明"我们是同一封信"？——靠发送端塞进帧里的一个小标签：R-TAG（冗余标签，6 字节，EtherType = 0xF1C1）。

字段长度作用
EtherType（0xF1C1）2 字节告诉沿途交换机"我是带冗余标签的帧"
路径/成员 ID（含版本与保留位）2 字节这份副本属于哪条成员流（走哪条路）
序号2 字节同一帧的两个副本序号相同，接收端按"流 + 序号"去重

接收端的消除逻辑（每条流维护一份"已收序号"记录）：

flowchart TB IN["收到一份副本<br>（带 R-TAG：流 + 序号）"] D["判断：查该流的已收序号记录<br>这个序号收过吗？"] NEW["没收过 → 新副本<br>记录序号，放行给上层"] DUP["收过了 → 重复副本<br>直接丢弃"] APP["上层应用：每份数据只收到一次"] IN --> D D -->|"没收到过"| NEW D -->|"已收到过"| DUP NEW --> APP

要点：同一个序号只放行一次。 先到的副本被放行并记录；后到的同序号副本一看"收过了"，直接丢弃。两份副本谁先到都行——结果都一样：应用只收到一份。

序号用完了怎么办？ 序号只有 16 位（0~65535），发满会回绕成 0。工程上接收端不是简单地"见重复就丢"，而是用滑动窗口判断新旧：序号比窗口内已收的新 → 放行；落在窗口内的旧序号 → 重复，丢弃；明显比窗口旧很多 → 按"回绕后的新帧"处理。这样既去了重，又不会把回绕后的新帧误杀。

五、两条路必须"真分开"——单点故障是冗余的天敌

FRER 有个前提：两条路径不能有"共同的致命弱点"。如果两份副本其实共享同一根线、同一个连接器、同一台交换机、同一个电源——那这个共享点一坏，两份一起死，冗余形同虚设。

共享点后果
同一根线束 / 同一个连接器线断 / 插头松 → 两路同时断
同一台交换机交换机挂 → 两路全没
同一个电源域电源失效 → 收发两端全趴窝

车里怎么落地：

  • 路径 A、B 走不同的交换机端口（甚至不同交换机），VLAN 也分开——上一课的 VLAN/流分类正好派上用场：为两条成员流建不同 VLAN，配合流分类保证各自带宽不被挤占；
  • 线束分开走线（左/右、前/后不同走向），避免一起被磨断；
  • 关键执行器（转向、制动）的冗余链路甚至要求独立供电——这已经属于系统级冗余设计，网络只是其中一环。

六、车上怎么用：只给"最不能丢"的流开 FRER

FRER 的代价是带宽翻倍 + 硬件支持（交换机要能解析 R-TAG、按流维护序号状态，通常需要支持 802.1CB 的车规交换芯片）。所以车上不是所有流量都开 FRER，只给"丢一条就出事"的流开：

流量开 FRER？理由
智驾域控 → 线控转向/制动（SBW/EMB）✅ 开安全关键闭环，丢一条都不可接受
ADAS 控制 / 功能安全相关报文✅ 开fail-operational 的硬要求
摄像头视频流❌ 不开带宽翻倍太贵，丢帧可容忍、可恢复
诊断、OTA、娱乐❌ 不开非实时，丢了重传即可
一句话：FRER 是把"带宽翻倍"的钱，花在"绝不能丢"的流上——它是 TSN 家族里"可靠性"维度的标准，和 Qbv（准时出门）、Qci（限速监管，后续会讲）配合使用。

七、把这几课串起来：一条关键指令的完整旅程

回顾车载以太网深度系列：PHY（L48）把帧变成电信号 → 交换机/流分类（L49）把帧分拣隔离 → TSN Qbv（L47）让帧准点出门 → FRER（本课）让帧"断一条路也不丢"。一帧转向指令的旅程：

  1. 智驾域控生成指令 → 复制功能复制两份、打上相同序号的 R-TAG；
  2. 两份分别进 VLAN 10 / VLAN 20，走两条物理链路；
  3. 沿途交换机按流分类放行——不拥塞、准点；
  4. 接收端消除功能：先到的一份放行，后到的重复副本丢弃；
  5. 执行器拿到恰好一份指令——即使其中一条链路已经断了。

八、三条铁律（记住这三句）

  1. "无缝"不是修得快，而是根本不用修——FRER 在故障发生前就把副本发出去了，一条路断了另一份照样到，切换时间 ≈ 0；等丢包再重传，对 1~10 ms 的控制闭环永远来不及。
  2. 去重靠"同一个序号只放行一次"——发送端用 R-TAG 给同帧副本打相同序号，接收端按"流 + 序号"放行先到者、丢弃后到者，上层永远只看到一份。
  3. 两条路必须真分开，共享点 = 单点故障——同一根线、同一个连接器、同一台交换机都会让冗余失效；FRER 只开给转向/制动这类"绝不能丢"的流，因为它的代价是带宽翻倍。
