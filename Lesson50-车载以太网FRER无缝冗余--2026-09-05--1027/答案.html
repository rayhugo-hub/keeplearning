车载以太网 FRER 无缝冗余——关键数据怎么"双路齐发、只收一份"？

费曼简答题参考答案

Q1：用"寄重要文件"的类比讲 FRER：为什么发两份？收件人怎么知道两份是同一份文件、不会读两遍？为什么两条邮路必须"真的不一样"？（提示：寄出前要在两份上做什么记号？两条邮路如果其实共享同一段路会怎样？）

核心思路：FRER = "寄一份绝不能丢的重要文件"——事前发两份走两条真不一样的路 + 靠同一个流水号去重，收件人永远只读到一份。
寄文件类比802.1CB 对应物
绝不能丢的重要文件转向/制动等安全关键帧
抄两份、盖同一个流水号复制功能 + R-TAG 里相同的序号
两条不同的邮路两条成员流（不同线束/交换机/VLAN）
收件人按流水号登记消除功能：同序号只放行一次
两份都共享同一辆车/同一座桥单点故障（同一根线/连接器/交换机）

三个问题逐一回答：

  1. 为什么发两份？ 任何一条邮路都可能出意外（车翻了、信湿了、送信人病了）——发两份、走两条不同的路，只要至少一条送到，文件就不丢。对应车上：一条链路可能被磨断、连接器松脱，两条独立链路同时坏的概率极低，所以"断一条也不丢"。
  2. 怎么知道是同一份、不会读两遍？ 寄出前在每份上盖同一个流水号（对应 R-TAG 的序号）。收件人按流水号登记：第一个到的号没见过 → 收下；另一份同号的到了 → 一看号已经收过 → 知道是重复件，不再读第二遍（丢弃）。所以不会读两遍，也不会漏收。
  3. 两条邮路为什么必须"真的不一样"？ 如果两条"邮路"其实共享同一段路（同一辆车转运、同一座桥），这段路一断，两份一起丢——共享点就是单点故障。对应车上：两份副本不能走同一根线束、同一个连接器、同一台交换机，否则那个点一坏，冗余就失效。

结论： 事前双发 + 按流水号去重 + 路径真分开，三者缺一不可——这就是 FRER 的完整逻辑。

Q2：为什么"发现丢了再补发"这一招，对转向、刹车指令来说来不及？把"等超时 → 通知对方 → 对方重发 → 再送到"这条链为什么慢讲清楚；FRER 为什么能做到"断了一条路也不卡顿"？

核心思路：重发是事后补救链，每一步都要花时间；FRER 是事前冗余——故障发生前副本就已经在两条路上，所以"无缝"。

补发为什么慢（一条事后链，环环都要时间）：

环节为什么慢
① 接收端发现丢了要靠"序号空洞"或"超时没等到"判断，至少得等一个帧周期
② 把"我丢了"报告给发送端又花一个网络来回
③ 发送端重新发送再花一个网络来回
合计≥ 2~3 个网络来回，且假设反馈通道本身没坏

而转向/刹车指令的周期可能只有 1~10 ms——等待期间执行器一直"听不到"新指令，车已经偏出去了；重传还会在拥塞时雪上加霜（越堵越重发，越重发越堵）。

FRER 为什么"断了一条路也不卡顿"： 它把"补救"变成了"预防"——故障发生之前，发送时就已经把帧复制成两份、分两条路发出。链路断掉的那一刻，另一份副本要么已经到了、要么正从另一条好路上赶来。接收端根本不需要"发现丢失"这个动作，也就没有反馈、没有等待，切换时间 ≈ 0。

结论： "无缝"不是修得快，而是压根不需要修——代价是平时带宽就翻倍，所以只给最关键的流开 FRER。

Q3（进阶）：接收端怎么保证"不多收、不漏收"？讲讲序号在其中起的作用：如果序号是 16 位，发满 65535 后会回绕成 0，接收端怎么避免把"回绕后的新帧"误判成"重复的旧帧"？（提示：滑动窗口，怎么判断新旧）

核心思路：不多收靠"同序号只放行一次"，不漏收靠"两条路各有一份"；回绕问题靠滑动窗口 + 序号差判断新旧，而不是"相等即重复"。

① 不多收——靠序号去重： 发送端给同一帧的两个副本打相同序号；接收端每条流维护一份"已收序号"记录：先到的副本 → 序号没见过 → 放行并记录；后到的同序号副本 → 查记录发现已收过 → 判定重复，直接丢弃。所以应用永远只收到一份。

② 不漏收——靠双路冗余： 两条路各有一份副本，正常时至少一份能到；一条断了，另一份照常到达，所以应用不会收不到。（除非两条路同时坏——这正是"路径必须真分开"的原因。）

③ 序号回绕——为什么"相等即重复"会出事： 16 位序号 0~65535 循环使用，65535 之后回到 0。如果接收端只记住"最后收到的序号"，下一帧是回绕后的新序号，简单判重复会把回绕后的新帧误杀。

④ 工程解法——滑动窗口： 接收端维护的不是"一个号"，而是一小段"最近已收序号"窗口，用序号差（按 65536 取模的意义上的"先后"）判断新旧：序号比窗口更新 → 放行，窗口滑动；序号落在窗口内 → 重复副本，丢弃；序号看起来旧很多（差值极大，只可能是回绕）→ 按"回绕后的新帧"放行。

结论： 接收端记的是"最近一段窗口"而不是"最后一个号"，新帧只有落进窗口才算重复——既去了重，又不会错杀回绕后的新帧。

选择题答案

MCQ1：FRER（帧复制与消除）相比"丢包后重发"，本质优势是什么？

✅ C. 故障发生前数据就已经复制成两份在路上，一条链路断了另一份照常到达，无需等待补救

解析：FRER 的本质是事前冗余：发送时就把帧复制成两份、走两条独立链路，故障发生时另一份副本已经在（或正在）路上，接收端无需发现丢失、无需反馈、无需等待，切换时间 ≈ 0——这才是"无缝"。A 说反了：FRER 平时就发两份，带宽 ×2；B 描述的仍是"事后重发"思路，只是把重发加快，依然要等"发现丢失 → 反馈 → 重发"整条链，对 1~10 ms 的控制闭环来不及；D 错误：FRER 恰恰依赖交换机/车规交换芯片支持（复制帧、打 R-TAG、按流维护序号状态），不是设备直连就能用。

MCQ2：接收端在同一条流上先后收到两份序号相同的副本，正确的处理是？

✅ B. 查已收序号记录：该序号已经收过 → 后到的是重复副本，直接丢弃，只放行先到的那份

解析：接收端去重的核心规则就是"同一个序号只放行一次"——先到放行并记录，后到同序号的判定重复直接丢，不多收也不漏收。A 把去重责任推给应用：应用层无法区分"两份副本"和"两条新指令"，还得自己做去重和时序处理，违背 FRER"对上层透明"的设计目的；C 回复发送端是多此一举，还引入反馈延迟（这正是 FRER 要消灭的东西）；D 两份都丢会造成漏收——万一其中一份是唯一到达的副本（另一条路已经断了），丢掉它应用就真的收不到了。

MCQ3：智驾域控到后轮转向执行器的 FRER 冗余，两条路径分别走左、右线束，但最终汇合在同一个连接器里。这个设计的最大问题是？

✅ D. 连接器成了单点故障——它一坏，两条路径同时失效，冗余白做

解析：FRER 成立的前提是两条路径物理上真正独立。左、右线束虽然分开了，但汇合在同一个连接器——这个连接器就是共同故障点（单点故障）：它一松脱/损坏，两份副本同时断在路上，冗余形同虚设。A 错误：FRER 要的是物理上不相交的路径，"逻辑上不同"（比如只是 VLAN 不同但走同一根线）不顶用；B 错误：交换机只能按拓扑转发，连接器是物理层故障，它既感知不到也无法"绕开"；C 错误：不存在这种"自动切换成单路"的机制——需要切换本身就是 FRER 要避免的事后补救。正确设计：线束分走、连接器也分开，最好再独立供电。
