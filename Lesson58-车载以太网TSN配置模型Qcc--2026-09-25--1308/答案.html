费曼简答题参考答案

Q1：用"去餐厅吃饭"打比方讲清三种配置模型；为什么"顾客只说想吃什么、别说用哪口锅"这么重要？

核心思路： 没有中心的时候，客人只能挨个窗口问；有中心的时候，点菜和排产分开，说需求的人不必懂后厨。

① 全分布式 = 一群客人自己跑到每个窗口挨个问

  • 一位客人想吃一道菜，就走到第一个窗口问 "你这儿还做得下吗"，窗口说做得下就记一笔，再由这个窗口去问下一个窗口，一直问到最后一个窗口，最后回来告诉客人可以了。
  • 问题在于：每个窗口只知道自己的锅有多大，谁也不知道全店今天总共能做多少菜；没人知道"这道菜到底几点能端上桌"——端上桌的时间要靠从下单到出菜一路上每个窗口都算一遍；客人想点一道需要两口锅同时做的菜，这套办法根本安排不了，因为没有任何一个人同时看得见两口锅。

② 全集中式 = 客人把想吃的统一报给前台

  • 前台只做一件事：把每位客人的需求收集齐、问清楚（几个人吃、要几个菜、最快多久要上），然后把整本需求交给后厨的总厨；
  • 总厨手上有全店的锅位图、每口锅的档期、每个传菜口的速度，由他来算谁先做、在哪口锅做、什么时候端出去；
  • 算完把每个窗口该做什么菜写成单子发下去，各窗口照单干活。

③ 混合式 = 客人照旧自己跑到窗口点，后厨另有一位总厨在边上听着

  • 他听见客人点了什么，虽然客人自己安排不了那些需要两口锅的菜，总厨可以顺手把它补上、把需要配合的部分安排掉。客人不需要改自己的习惯，店里却多了一份全局安排。

④ 为什么"顾客只说想吃什么、别说用哪口锅"这么重要

  • 需要两口锅同时开火这件事，是后厨的结构决定的能力。一个只想着"我要吃这道菜"的客人，不可能知道全店今天还有没有空锅、几号锅现在正忙着别的菜。
  • 如果让客人自己去指定锅，他就必须知道全店的锅位图、每口锅的档期、每道菜占锅多久，还得随时应付别人也在点菜带来的变化——他既没有这个信息，也不该背这个责任。
  • 反过来，让客人只说需求（要什么菜、多久要上），后厨就能在信息齐全的情况下自己想最优安排；客人换了菜也只需要重新报一次需求，后面全部重新算一遍即可。
  • 这就是"点菜与排产分开"的价值，也是整套自动化配置能成立的前提。

Q2：收集需求的一方和算配置的一方各管什么？为什么用户只该说需求？算不出来时该怎么回答？

核心思路： 一方把用户的话问清楚并汇总，另一方掌握全网情况负责算账；用户只出需求不出配置，算不出来必须明说。

① 收集需求的一方（站在用户这边）

  • 主动去问每个应用"你要发什么样的流"，把答案整理成统一的说法：多久发一次、一个周期里最多几帧、每帧最大多少字节、最晚多久必须送到、要不要冗余路径；
  • 检查这些说法有没有漏、有没有自相矛盾，最后把多份需求汇总成一本清单往上交；
  • 它不需要懂门控表，也不该替用户拍板，它只保证"用户想说的话，被准确、完整地翻译成了网络能理解的需求"。

② 算配置的一方（站在网络这边）

  • 手里有全网的连接关系和每段链路的容量；
  • 给每条流找一条走得通的路；
  • 算出这条路上每一跳该怎么配（哪个队列、开多宽的窗口、留多少带宽、要不要挂流过滤器、冗余的两条路各走哪边）；
  • 逐跳检查资源够不够；
  • 把每个节点该配什么写成配置真正写进每一台交换机，并把结果回报给用户。

③ 为什么用户只该说需求、不该说配置

需求语言配置语言
谁知道应用自己最清楚取决于全网别的流 + 每台交换机的队列 + 谁开在第几微秒不撞车
信息在哪应用本地只存在于网络侧
改了怎么办重报一次需求即可一旦写死，网络侧就没法重新算
  • 让用户去指定配置，等于把全局信息塞进一个看不见全局的人手里——他必须先知道全网所有别的流、所有交换机的结构，还要跟得上别人改动的变化。这在现实里做不到，做错了还会互相踩。

④ 资源不够时应该怎么回答

  • 应该明确告诉用户这条流建不起来，并说清是哪条要求没被满足、卡在哪一段链路上；
  • 让用户知道该降要求（时延放宽一点、帧率降一档），还是该改网络；
  • 价值在于：把违约当场暴露出来，用户还能据此调整。
  • 如果反过来"先答应下来、实际跑不到"，用户会以为自己的流是安全的，直到某天现场出现丢帧或时延超标才发现承诺是空的，而那时已经很难定位。这与 L57 ATS 的"超规格直接丢帧"是同一种性格：宁可当场拒绝，也不把问题藏进缓存里慢慢恶化。

Q3（进阶）：为什么要重新解算而不是只改一个数？为什么配置要和软件同版本？下发与生效差哪一步？两种模型各自的代价？

核心思路： 一条流的参数不是它自己的事，而是和别人的流共用资源算出来的；配置是软件行为的假设；下发不等于生效。

① 为什么不是只改一个数

依赖说明
这条流自己的规格间隔、帧长、时延上限
同链路别人的流共用同一段链路、同一个队列
拓扑与链路容量路径能走多远、每跳剩多少余量
  • 多一路摄像头，不只是"多了一条流"——它占掉沿途每一跳的队列时间，可能把原来某条流的窗口挤掉、把某个队列的信用额度分薄；
  • 所以要做的不是改一个数字，而是把所有相关流放在一起重新解一遍：重新找路、重新排窗口、重新检查每一跳还够不够；
  • 只改一个数，很可能顾了自己、坑了别人。

② 为什么配置必须和软件绑在一起

  • 应用的行为建立在一个假设上：它以为自己每毫秒发一帧、半毫秒内一定到，而这个假设是由网络侧配置撑起来的；
  • 软件换了、节奏变了，网络还按旧配置服务 → 应用在完全不知情的情况下跑在不成立的前提上，表现就是莫名其妙的时延超标或丢帧；
  • 反过来，配置先换、软件还是旧的，也对不上；
  • 所以配置和软件必须作为同一个版本一起登记、一起下发、一起回滚，谁都不能单独跑。

③ 下发和生效之间差哪一步

  • 下发 = 配置被写进了每台交换机的存储；生效 = 它真的在跑；
  • 中间可能出各种岔子：某台交换机的固件版本不同、参数不被识别；线束接错导致拓扑与预期不一致；某台设备重启后配置被复位；甚至有人现场手改过某台设备；
  • 所以要能反过来读：把每台交换机实际正在用的配置读回来，与预期的那一份逐项比对，对不上的当场发现，而不是等出了故障再倒推。

④ 两种模型各自的代价

好处代价
全分布式不需要中心；设备坏了各管各的没人看得见全网：只能回答"还有没有带宽"，答不出端到端最晚什么时候到，排不出需要全网协同的窗口安排，规模一大就乱
全集中式有全局视图，参数能被算准、能配门控表 / 冗余 / 流过滤引入了一个中心：中心算不出来或不在线，新流就建不起来（关键配置最好能离线预置）；要求用户把流量规格说清楚，说不清就配不出来；改一个参数要走"改规格 → 重新算 → 再下发"的完整链路，现场手改一台设备的日子结束了

⑤ 已经量产的平台怎么选

  • 选"网络侧集中、用户侧仍用老办法"的那一种：端站照旧自己说话（不用改已经量产的软件）；网络侧加一个中心实体听着，把老办法根本算不出来的那部分——比如每跳的窗口安排、冗余的两条路——补上。
  • 既不动量产软件，又能把确定性提上来，是现实中阻力最小的走法；等下一代平台再说全集中。

选择题答案

MCQ1：关于 IEEE 802.1Qcc 定义的三种配置模型，哪项描述最准确？

✅ B. 全分布式：端站用 SRP 逐跳协商，没有任何中心实体；全集中式：用户侧由 CUC 收集需求、网络侧由 CNC 算参数并下发，端站也由中心配置；集中式网络 + 分布式用户：网络侧有 CNC（看得见全网），但端站仍用 SRP 说话，CNC 从网络里听出有哪些流，再补算 SRP 算不出来的参数

解析：B 正确——三种模型的分界线就是"谁掌握全局视图"：全分布式端站自己举手、逐跳协商；全集中式用户侧（CUC）与网络侧（CNC）都由中心配置；混合式网络侧集中、用户侧仍走 SRP，由 CNC 补算门控表 / 冗余成员这类 SRP 里没有的概念。A 错：802.1Qcc 不是在讲静态配置 / DHCP / gPTP 同步——它讲的是流预留与配置的架构分工，而 gPTP 是时间同步（802.1AS），属于另一个标准。C 错：全分布式恰恰是没有任何中心实体；"每台交换机都跑一个 CNC 再互相协商"在标准里不存在，那等于把中心散成一堆，既不集中也不分布，解决不了"谁看得见全网"的问题。D 错：三种模型的区别是"谁算参数"，不是"用不用时钟"；事实上集中式模型里的 CNC 通常要借助同步时间做测量与校验，但与"是否使用 gPTP"不是分类依据。

MCQ2：在集中式模型里，CUC 与 CNC 的分工，哪项最准确？

✅ C. CUC 面向用户 / 应用，负责把"应用要发什么样的流"收集成需求（发送间隔、每周期帧数、最大帧长、最晚时延、要不要冗余）；CNC 面向网络，掌握拓扑与链路容量，负责算路径、算 TSN 参数（门控表 / 信用斜率 / 流过滤器 / 冗余成员）并把它下发到交换机；两者之间通过 UNI 交互

解析：C 正确——CUC = 用户侧的需求收集者（站在应用这边，说的是"要什么"）；CNC = 网络侧的算账人（站在网络这边，说的是"怎么配"）；两者之间是 UNI；这条分工就是"需求与配置分离"的落地形态。A 错：给交换机下发配置的是 CNC，不是 CUC——CUC 不碰交换机，它连拓扑都不掌握，只面向端站（应用）；把两者职责对调，正好把整套架构的意义丢掉了。B 错：CUC 与 CNC 功能完全不同，不是同一台设备的两种叫法：一个是"把用户的话问清楚"，一个是"把网络配明白"；合在一起就没人替用户把关口径、也没人把全网资源算清楚。D 错：方向反了——门控表是网络侧的产物，由 CNC 算；CUC 既不计算门控表，也不把门控表"翻译成需求"，它做的是反向的事：把用户的需求翻译成网络能理解的形式交上去。

MCQ3：关于"全分布式（SRP）为什么撑不住、802.1Qcc 补了什么"，哪项最准确？

✅ D. SRP 是逐跳协商、没有全局视图，只能回答"带宽还够不够"，答不出"端到端最晚什么时候到"，也排不出全网门控表、推不出 FRER 的不相交双树，规模与收敛也受限；802.1Qcc 提高了可支持的流数量、缩短了流的建立与拆除时间，并引入 UNI 与基于 YANG 数据模型的配置通路，让参数可以由中心算好后统一下发

解析：D 正确——把 SRP 的四个硬伤（无全局视图、答不出端到端时延、算不出需要全网协同的门控表 / 不相交双树、规模与收敛受限）与 Qcc 的三条增强（提高流数量上限、缩短流建立 / 拆除时间、引入 UNI 与 YANG 配置通路）说全了。A 错：SRP 不依赖 gPTP——它压根不需要全网时钟，靠的是逐跳的带宽登记；说"SRP 必须依赖全网同步、Qcc 去掉了时钟"把 SRP 和 Qbv 混了。B 错：SRP 排不出全网门控表——门控表是"谁的窗口排在第几微秒、不能撞车"的全网组合优化问题，逐跳协商根本不具备这个视角；这不是"下发慢"的问题，是根本没有这个能力。C 错：802.1Qcc 没有取消 SRP，恰恰相反，它增强了 SRP，并保留了"端站用 SRP"的全分布式与混合模型；说"所有端站都必须直接跟 CNC 说话"是把"三种模型可选"误读成"只有一种"。

本节速记卡

要点一句话
一句话定义802.1Qcc 定义的是 TSN 的配置架构：谁有全局视图、谁算参数、怎么把参数下发到每台交换机
三种配置模型全分布式（端站 SRP 逐跳协商，无中心）、全集中式（CUC + CNC）、集中式网络 + 分布式用户（网络侧集中、用户侧仍 SRP）
全分布式的问题没有全局视图：只答得出"带宽够不够"，答不出"端到端最晚什么时候到"，排不出门控表、推不出不相交双树
CUC站在用户 / 应用这边，负责收集与汇总需求（间隔、每周期帧数、帧长、时延、冗余）
CNC站在网络这边，掌握拓扑与容量，负责算路径 + 算参数 + 逐跳检查 + 下发
UNI用户 / 网络接口：把"我要什么"翻译成"网络怎么配"的那道口
需求三件套TrafficSpecification（流量规格）、UserToNetworkRequirements（时延 / 抖动上限 / 要几条无缝冗余路径）、InterfaceConfiguration（MAC / VLAN）
用户不该说什么不该说配置（门控表、idleSlope、流过滤器）——那些取决于全网别人的流和交换机结构，用户看不见
算不出来怎么办明确报失败并说清卡在哪条要求、哪段链路；不降级、不硬发（与 ATS"超规格直接丢帧"同一种性格）
下发通路CNC 通过基于 YANG 数据模型的管理协议（NETCONF / RESTCONF）把配置写进每台交换机
混合模型的意义端站不用改，网络侧加 CNC 就能补上 SRP 算不出来的东西 → 存量平台升级的现实路径
功能一变不是"改一个数"，而是"重新解一遍题"：流自己的规格 + 同链路别人的流 + 拓扑容量
配置与软件配置是软件行为的假设，必须同版本下发、同版本回滚
下发 ≠ 生效还要读回每台交换机的实际配置与预期逐项比对
集中式的代价引入中心（要能离线预置）、配置成本前移（规格必须说清楚）、修改链路变长、依赖配置纪律
一句话边界用"把需求与配置分开 + 一个能看见全网的中心"，换"参数算得准、改得动、可核对"
