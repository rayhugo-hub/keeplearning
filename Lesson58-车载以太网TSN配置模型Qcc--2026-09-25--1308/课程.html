一、先想想这个场景：机制都学会了，可这些数到底谁填？

前面十一课，我们把车载以太网的"工具箱"一件一件拆开了。现在把它们摊在桌上，你会看到一个共同点——每一件都要填参数：

机制在哪一层动手它要填进去的参数
VLAN / 流分类（L49）二层转发VLAN ID、PCP 优先级、流特征
Qbv 门控（L47）出口队列门控表（GCL）：谁在第几个微秒开门
Qav 信用整形（L55）出口队列idleSlope / sendSlope
CQF 循环排队（L56）队列对全网统一的节拍 T
ATS 异步整形（L57）每条流TokenRate / TokenBurst / MaxResidenceTime
PSFP 每流监管（L53）入口流过滤器、流门控窗口、令牌桶
帧抢占（L54）MAC 内部谁能抢谁
FRER 无缝冗余（L50）双路径成员流、R-TAG、消除功能
MACsec（L52）链路密钥与安全通道

问题就这么冒出来了：

全车几十上百条流、几十台交换机，这些参数到底谁算？算完怎么送到每一台交换机上？车 OTA 加了个新功能，谁重新算一遍？

这就是 TSN 的"配置平面"问题——机制在数据平面，参数在配置平面，配置平面塌了，数据平面再漂亮也跑不起来。

答案写在 IEEE 802.1Qcc（2018，已并入 802.1Q 主标准）里。它的全名是《流预留协议（SRP）增强与性能改进》，听起来像给老协议打补丁，其实它引入的正是TSN 的配置架构。

二、一个概念：三种"谁说了算"的配置模型

802.1Qcc 定义了三种（互斥的）配置模型。它们的区别只有一个：谁掌握全局视图、谁负责算参数。

2.1 全分布式（Fully Distributed）——老办法，端站自己举手

没有中心实体。 Talker 用 SRP（MSRP） 宣告"我要发这么一条流，长这样、要这么多带宽"，交换机逐跳往下传，沿途每一台各自检查"我这里的带宽还够不够"，够就登记下来，最后 Listener 收到后回一个"Ready"。

整套动作是逐跳、分布式协商出来的，没有任何一个设备看过全网。

2.2 全集中式（Fully Centralized）——用户侧和网络侧各有一个"管事的"

这里出现了两个新角色，是整个 TSN 配置体系的核心：

角色站在谁那边干什么
CUC（Centralized User Configuration，集中式用户配置）用户 / 应用这边主动去问端站"你要发什么样的流"，把需求收集、汇总、检查口径
CNC（Centralized Network Configuration，集中式网络配置）网络这边掌握拓扑与每段链路的容量；算路径、算参数；把配置下发到每台交换机；把结果回报给用户

两者之间通过 UNI（User/Network Interface，用户/网络接口） 交互。端站与 CUC 之间也是 UNI 的另一种形态。

2.3 集中式网络 + 分布式用户（Centralized Network / Distributed User）——混合

网络侧是集中的（有 CNC，看得见全网），用户侧仍是分布式的（端站照旧用 SRP 说话，不改成向 CUC 上报）。

CNC 从交换机里听出"现在有哪些流被登记了"，然后再补上 SRP 自己算不出来的东西——比如 Qbv 门控表、FRER 冗余成员、PSFP 流过滤器。这条路的现实意义很大：老设备不用改，只要网络侧加一个 CNC 就能把确定性提上来。

三、UNI 的意义：把"我要什么"和"网络怎么配"分开

这是全课最值钱的一个观念。

用户（应用开发者）说的是需求语言：

我要每 1 ms 发 2 帧，每帧最大 1500 字节，全网最晚 500 µs 必须到对端，而且我希望路径冗余。

网络（TSN 工程师）说的是配置语言：

这条流打 VLAN 10、PCP 6；在 3 号交换机的 6 号队列上加一条门控表项、开窗 64 µs；4 号交换机的 idleSlope 改成 20 Mbps；入口挂一个流过滤器；两棵不相交的转发树各发一份、R-TAG 序号递增。

这两句话之间隔着一整个专业领域的知识。UNI 就是这道翻译口。

在 UNI 上流动的信息，802.1Qcc 归纳成三件套：

三件套谁提供装什么
TrafficSpecification（流量规格）用户发送间隔（Interval）、每周期最多几帧、最大帧长（MaxFrameSize）、按哪个流量类别 / 优先级走
UserToNetworkRequirements（对网络的要求）用户最大时延（MaxLatency）、时延抖动上限（MaxLatencyVariation）、需要几条无缝冗余路径（NumSeamlessTrees，就是 L50 FRER 的"要几棵树"）
InterfaceConfiguration（接口配置）用户用哪个 MAC 地址、打不打 VLAN 标签、标什么
用户永远不需要知道门控表长什么样、idleSlope 填多少、门在第几微秒开。 他只说"我要多快、多晚、多可靠"，翻译是网络侧的事。这就是 UNI 的全部价值。
flowchart LR APP["应用 / 端站<br/>我要每 1 ms 发 2 帧，每帧最大 1500 字节<br/>最晚 500 µs 到，而且要冗余"] --> UNI1["UNI<br/>用户语言：需求"] UNI1 --> CUC2["CUC<br/>汇总所有应用的需求<br/>检查口径是否说清楚"] CUC2 --> CNC2["CNC<br/>算路径、算参数<br/>逐跳检查全链路资源够不够"] CNC2 --> CFG["网络语言：配置<br/>VLAN / 门控表 / 信用斜率<br/>流过滤器 / 冗余成员 / 密钥"] CFG --> SW["沿途每台交换机<br/>照着下发下来的配置生效"]
反过来也成立：网络侧答不上来时，也要用用户听得懂的话回答——"你的要求我满足不了，因为第 3 段链路容量不够"，而不是甩一张门控表给应用开发者自己看。

四、一次"集中式下单"的完整流程

把全集中式模型的一次流水走一遍，就明白它到底在解决什么：

sequenceDiagram participant T as Talker 应用端站 participant C as CUC 用户侧 participant N as CNC 网络侧 participant S as 沿途交换机群 participant L as Listener 应用端站 T->>C: 我要发一条流（流量规格 + 对网络的要求） C->>N: 汇总后的需求（经 UNI） N->>N: 算路径、算参数、逐跳检查资源 alt 能满足 N->>S: 把配置下发到沿途每一台交换机 N-->>C: 成功（附这条流的网络侧参数） C-->>T: 你的流可以按这个规格发了 C-->>L: 准备接收这条流 T->>L: 按约定的节奏发数据 else 不能满足 N-->>C: 失败（附原因：哪条要求没被满足） C-->>T: 这条流建不起来（明确告诉你为什么） end

这里面有四个容易被忽略的设计要点：

  1. 需求是"声明式"的，不是"命令式"的。用户只声明结果（间隔、帧长、时延上限），怎么实现由网络侧决定。这跟"你直接告诉我往哪个队列写什么"是完全不同的思路，也是能自动重算的前提。
  2. CNC 需要一张拓扑图。这张图通常来自链路层发现（LLDP 之类）自动学习，也可能在整车开发阶段就离线给定——车上的网络是设计出来的，拓扑本来就已知。
  3. 算不出来要明确报失败。这是全课最"工程师"的一条：CNC 发现资源不够时，不降级、不硬发，而是返回失败并把原因说清楚。这跟 L57 ATS 的"超规格直接丢帧"是同一种性格——宁可把违约暴露出来，也不让它无声恶化。
  4. 配置只是"一次下单"，不是"一直生效"。流拆除、链路故障后重路由、功能变更，都要重新走一遍这个流程（或者由故障恢复机制接管）。

五、那老办法（全分布式 SRP）为什么撑不住？

SRP / MSRP 是传统 AVB 时代的产物，它在"几条音频流"的规模上很好用，但放到整车级确定性网络上有四个硬伤：

硬伤说明
没有全局视图每台交换机只知道自己的端口和队列。它能回答"我这还有带宽"，答不出"端到端最晚什么时候到"——端到端时延要沿着整条路径把每跳的干扰都算上
算不出门控表Qbv 的门控表是个全网协同的组合优化问题（谁的窗口排在第几微秒、不能撞车），逐跳各自为政根本排不出来；FRER 的"两棵不相交的树"更不可能由逐跳协商推出来
收敛与规模受限宣告要一跳一跳扩散、Ready 要一跳一跳回传，节奏由协议计时器控制，一条流的建立不是瞬时的；而且 SRP 原本能承载的流数量级别，与"整车几百条流"不是一个量级
改一处就要重新协商功能一变（加一路摄像头、改一个帧率），原来的登记关系要重新走一遍流程，且没有任何一方能判断这次变更会不会把全网的预算挤爆

802.1Qcc 对 SRP 做的增强，方向就是这三条：

  • 提高可支持的流数量上限（Qcc 的目标是把可支持的流数量提到 2 的 32 次方这一量级，早期 SRP 的规模远达不到）；
  • 缩短流的建立与拆除时间，让流的创建 / 删除不再慢吞吞；
  • 引入远程配置与基于 YANG 数据模型的配置通路，让门控表、信用斜率、流过滤器、冗余成员这些"SRP 里根本没有的东西"可以被中心算好后统一下发。
下发用的是一条通用的网络管理通路：CNC 通过基于 YANG 数据模型的管理协议（NETCONF / RESTCONF）把配置写进每台交换机。802.1Q 用 YANG 把"桥有哪些可配的东西"描述成机器可读的结构（桥、VLAN、端口、队列、门控、流过滤……），CNC 只要按这套结构填值就行——这是"配置能自动化"的技术底座。

六、工程要点：OTA 改了功能，TSN 配置怎么办

这是整节课最贴近实际工作的一问。车上一条流的 TSN 参数，依赖三个东西：这条流自己的规格、同一条链路上别人的流、拓扑与链路容量。所以：

  1. 功能一变，配置就可能全变。多一路 4K 摄像头、ADAS 模型换了个推理频率、给后排加了路云游戏，都可能挤掉原来某条流的预算。这不是"改一个数"，而是"重新解一遍题"。
  2. 配置必须和软件一起版本化下发。TSN 参数是软件行为的假设——应用以为"我每 1 ms 发一帧，500 µs 必到"，网络却还在按旧配置服务，那就是悬空承诺。所以配置要和软件版本绑在一起登记、一起 OTA、一起回滚，配错版本等于配错功能。
  3. 配置是"算出来的"，不是"抄出来的"。整车级 TSN 配置通常离线解算（排门控表本身就是很难的组合优化问题），解出来的是一份配置文件 + 每个节点该配什么，随软件包一起上车。
  4. 上车后要核对生效配置。下发不等于生效——线束接错、交换机固件版本不同、某台的配置被复位，都会让实际生效的配置与预期不一致。要能读回每台交换机的实际配置并与预期比对。
  5. 渐进推进的现实做法：全集中式最"干净"但要求端站配合（要对 CUC 说话），整车换代才有机会；存量平台往往先走"集中式网络 + 分布式用户"——端站一行代码不改，网络侧加 CNC 就能把 Qbv / FRER 这些"SRP 算不出来的东西"补上。

集中式的代价也要说清楚：

代价说明
引入了一个中心CNC（以及 CUC）算不出来或不可用，新流就建不起来；所以关键流的配置通常要能离线预置，不依赖在线中心
配置成本前移好处是"上线即确定"，代价是开发阶段就要把流量规格说清楚，说不清就配不出来
修改链路变长想改一个参数，要先改规格、再解算、再下发，不能现场手改一台交换机了事
依赖配置纪律配置与软件必须同版本，谁擅自改一台设备的参数，都会让"账目"失效

七、三条铁律（记住这三句）

  1. 配置平面的三种模型，区别只在"谁有全局视图"：全分布式（端站 SRP 逐跳协商，没有中心）→ 只知道"还有没有带宽"，答不出端到端最晚什么时候到、排不出门控表；全集中式（CUC 面向用户收集需求 + CNC 面向网络算参数）→ 有全局视图，能配门控表 / FRER / 流过滤，但要求端站配合；集中式网络 + 分布式用户（网络侧有 CNC、端站照旧 SRP）→ 存量平台把确定性提上来的现实路径。
  2. UNI 的使命是把"我要什么"和"网络怎么配"分开：用户只说间隔 / 每周期帧数 / 最大帧长 / 最晚时延 / 要几条冗余路径，网络侧负责翻译成 VLAN、门控表、信用斜率、流过滤器、冗余成员。用户不需要懂门控表，网络侧也必须能用用户听得懂的话回答"为什么建不起来"。
  3. 配置是算出来的、要和软件一起版本化：参数依赖"这条流的规格 + 同链路别人的流 + 拓扑容量"，所以功能一变就得重新解题；算不出来要明确报失败而不是硬发；配置必须和软件同版本下发、同版本回滚，上车后还要读回每台交换机的实际配置去核对。

八、费曼简答题（用自己的话，不许用术语）

Q1：用"去餐厅吃饭"打个比方，讲清三种配置模型：谁是顾客、谁是传菜的服务员、谁在后厨算账、谁负责把菜做出来并端到每个桌上？（提示：全分布式就像一群客人自己跑到每个窗口挨个问"你这儿还做得下吗"，没人知道全店今天到底能做多少菜；全集中式是客人的需求统一交给前台，前台再交给后厨排产；混合是客人照旧自己跑去窗口点，但后厨另有一个总厨在边上听着，顺手把客人自己点不出来的菜——比如需要两口锅同时做的菜——给安排上。）再说清：为什么"顾客只说想吃什么、别说用哪口锅"这件事这么重要？

Q2：在集中式这套流程里，收集需求的那一方和算配置的那一方各管什么？为什么用户只该说"多久发一次、一次几帧、帧多大、最晚多久到、要不要冗余"，而不该说"给哪个队列写下什么门控表"？如果网络侧算了一圈发现资源不够，它应该怎么回答用户，为什么这样比"先答应下来、实际跑不到"要诚实？（提示：把违约暴露出来；跟 L57 里"超规格直接丢帧"是同一种性格）

Q3（进阶）：车 OTA 加了一个新功能（比如多一路高清摄像头），TSN 配置为什么要重新解算而不是只改一个数？为什么配置必须和软件版本绑在一起下发和回滚？"配置算完下发到交换机"和"配置真的生效了"，中间还差哪一步？最后说说：全集中式和全分布式各自的代价是什么——如果你接手的是一个已经量产的平台，端站暂时动不了，你会选哪种模型，为什么？（提示：重新解题的三个变量是流自己的规格、同链路别人的流、拓扑容量；读回核对；离线预置 vs 引入中心）
