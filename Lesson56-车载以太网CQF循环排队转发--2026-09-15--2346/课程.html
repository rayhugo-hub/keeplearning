一、先想想这个场景：时刻表算不动，信用整形又不保时延，中间那条路在哪

L47 学过 Qbv 门控：准点、能给硬时延上界。但它的代价很重——需要 gPTP 全网时钟同步、需要离线为每条流算出精确时刻表、需要逐跳都支持。而且网络一改（加一条流、加一个节点、改一个周期）就要从头重算。整车 OTA 加了几个新功能，时刻表就得重排一遍。

L55 学过 CBS 信用整形（Qav）：轻量，不需要全局时钟，配置就两条斜率一个门槛。但它只承诺"长期平均速率 + 有限突发"，给不了硬时延上界——它没法回答"这一帧最晚什么时候能出去"。

于是工程上出现了一块真空地带：

"我既不想算时刻表，又想要一个有保证的时延上界，能不能做到？"

IEEE 802.1Qch 给出的答案叫 CQF（Cyclic Queuing and Forwarding，循环排队转发），中文也常译作"循环队列转发"，业界把它和 CBS 一起归进"整形器家族"、并给它起了个形象的外号——"蠕动整形"（peristaltic shaper）。

它的思路朴素到令人惊讶：不逐流排时刻表，只做两件事——全网统一一个"节拍" T；每个出端口准备两个队列，奇偶节拍轮流当班。

二、一个概念：两个队列轮流"当班"，帧必须"换班"才准走

2.1 三条硬规则

时刻新到的帧进哪里哪个队列在发送
周期 n（偶数拍）写进 队列 A（等待席）队列 B 当班 → 整批发出
周期 n+1（奇数拍）写进 队列 B（等待席）队列 A 当班 → 整批发出
周期 n+2写进 AB 当班
周期 n+3写进 BA 当班
…奇偶交替，永不停止

规则只有三条：

  1. 本跳新到达的帧，只准写进"等待席"（不当班的那个队列）。
  2. 每经过一个固定周期 T，两个队列交换角色（等待席 ⇄ 当班席）。
  3. 任何一帧至少要在本跳待满一个周期才准被转发——不允许"本周期到达、本周期就发走"。
flowchart LR ARR["📥 周期 n：到达的帧全部写入<br>A 队列（等待席）"] --> SW{"⏱️ 周期边界到<br>交换角色"} SW --> SND["📤 周期 n+1：A 队列当班<br>整批连续发出"] SND --> ARR2["📥 同时：新到的帧写入<br>B 队列（等待席）"] ARR2 --> SW

2.2 为什么第 3 条规则这么关键

如果允许"本周期到、本周期就发"，那么同一个周期里早到的帧会挤在后到的帧前面——谁先谁后取决于到达时刻的微小差异，一跳到下一跳误差就放大，时延又会变得不可预测（这正是普通 FIFO 和 CBS 的老毛病）。

强制"等一个周期"以后，情况完全变了：

同一个周期内到达的一批帧，会被打包成"同一批"，一起在下一个周期出发。

这就是"蠕动"二字的来源——像蠕动泵一样，把连续的数据流切成一段一段、匀速地挤出去；也像旋转寿司 / 摩天轮：等待席是"上客区"，当班队列是"旋转中的盘子"。客人先在上客区坐满一个节拍，节拍一到整批换到旋转位，另一批开始上客。

flowchart TB subgraph HOP["一跳（一个出端口）内部"] WAIT["等待席队列<br>本周期到达的帧停在这里"] BUSY["当班队列<br>本周期被整批发出"] end TICK["⏱️ 周期定时器 T<br>（来自全网的节拍）"] --> ROLESWAP["角色交换：等待席 → 当班席"] ROLESWAP --> WAIT ROLESWAP --> BUSY WAIT --> OUT["端口仲裁 → PHY → 链路"] BUSY --> OUT

2.3 时延账：每跳 ≤ 2T，抖动只跟"相位"有关

一帧进入某一跳后，要等两件事：

等待项最坏时长为什么
① 等"换班"T它只能写进等待席，必须等下一个周期边界才能被换到当班席
② 等"前面发完"T换班后它排在当班队列里其他帧后面，最坏要等满一个周期
每跳停留合计≤ 2T最快几乎 0（刚好处在周期边界前到达、且当班队列为空），最坏 2T

但端到端并不是简单地把 2T 乘以跳数——因为"换班"这件事在全网是相位对齐的：

  • 帧在周期 n 到达桥 1 → 它一定在周期 n+1 离开桥 1；
  • 于是它在周期 n+1 到达桥 2 → 在周期 n+2 离开桥 2；
  • ……每过一跳，出发的周期号只 +1，误差不会被放大。

所以 H 跳（H 台交换机）的端到端时延上界是：

端到端时延 ≤ (H + 1) × T ——而且它只取决于"跳数 H"和"周期 T"，与网上有多少条流、每跳有多少帧在竞争无关（唯一前提：每周期不超容量，见第三节）。
机制时延上界上界取决于什么抖动会不会随跳数累积
普通 FIFO无（无界）—会（且随流数累积）
CBS / Qav无硬上界，只有"平均速率 + 有限突发"—会
CQF / Qch(H+1)·T跳数 H 与周期 T（与流数无关）不会（每跳只把周期号 +1）
Qbv 门控 + 时刻表可做得很紧逐流时刻表不会，但配置极重

三、周期 T 怎么选：一个"不能太小的下限 + 不能太大的上限"

CQF 只有一个旋钮——T。它同时也是唯一的事故源。

3.1 下限：T 必须"装得下"

约束 ①：T 必须大于最大帧的发送时间。
否则一个周期连一帧都发不完，帧会横跨周期，整个"等待席 / 当班席"模型直接失效。

约束 ②：每周期容量 ≥ 每周期到达量。
每周期容量 = 端口速率 × T（字节）。如果某类流量在一个周期里集中到达的量超过这个容量，装不下的部分只能滚到下一个周期——这一滚，2T 的上界和 (H+1)T 的端到端预算就同时失效了，严重时直接丢帧。

flowchart TB BURST["📦 某个周期集中到达 6000 字节"] --> CAP{"周期容量 = 速率 × T<br>装得下吗？"} CAP -->|"T 足够大 ✓"| OK["当周期整批发完<br>上界 (H+1)T 成立"] CAP -->|"T 太小 ✗"| BAD["余量被推到下一周期<br>上界失效 / 缓冲溢出丢帧"]

3.2 上限：T 越大，时延越大

端到端上界 (H+1)·T 随 T 线性增长——T 每翻一倍，时延预算就翻一倍。而且 CQF 的时延是"以周期为颗粒被量化"的：同一批帧不管早到晚到，都在同一个周期出发，代价是它们都至少被推迟到一个周期之后。这就是"用一点平均时延，换确定性和抖动"。

3.3 数值感受（100 Mbps 链路）

100 Mbps = 12.5 MB/s。

项计算结果
一个最大帧（1500 B 载荷）发送时间1500 ÷ 12.5 MB/s120 µs → 所以 T 必须 > 120 µs
T = 100 µs 时的每周期容量12.5 MB/s × 100 µs1250 字节 → 连一个 1500 B 帧都装不下 ✗
T = 500 µs 时的每周期容量12.5 MB/s × 500 µs6250 字节 ≈ 4 个 1500 B 帧 ✓
某类一个周期要发 4 帧（6000 B）→ T 至少要6000 ÷ 12.5 MB/s480 µs → 工程上取 500 µs 以上留余量
关键认知：T 不是"越小越好"。它必须同时满足"大于单帧时间"和"装得下最坏周期"，在这两条下限之上再尽量取小以压低时延。先算最坏周期的到达量，再反推 T，这是 CQF 配置的标准动作。

四、它和 Qbv / CBS / PSFP / FRER 的分工

机制位置提供什么保证配置成本与 CQF 的关系
Qbv 门控（L47）出口队列硬时延上界（可很紧）、准点高：gPTP + 离线逐流算表，改网必重算CQF 可以看作 Qbv 的一种"特化用法"：固定周期、两个队列 50% 占空比交替开关——不用为每条流算表，全网只要一个 T，但上界比精心排布的 Qbv 更松（以周期为颗粒）
CBS 信用整形（L55）出口队列平均速率 + 有限突发（无硬上界）低：两条斜率 + 一道门槛同一队列上一般选其一：要"速率有界"选 CBS，要"时延有界"选 CQF。CQF 的周期量化天然替掉了"信用攒额度"，代价是平均时延更大
PSFP 每流监管（L53）交换机入口入场资格、每流限速中CQF 的必需品：上界"与流数无关"的前提是每周期不超容量；超容量的流必须在入口被挡住或降级，否则 CQF 的承诺被撑破
帧抢占（L54）出口 MAC 内部削减"一个最大帧"的阻塞中可叠加：CQF 已经把一个周期内的阻塞量化掉；抢占进一步缩短非关键帧对关键帧的阻塞，让周期边界更干净
FRER（L50）双路径复制 / 去重链路失效不丢帧中周期与相位必须两侧一致：两条冗余路径的 CQF 节拍错开，去重窗口就得放大，等于把冗余换来的时延预算又送回去
MACsec（L52）/ PHY（L48）加密 / 物理层内容可信 / 比特上线—都吃帧长预算：ICV、各层标签让同一帧更长 → 每周期能装的帧数变少，反推 T 时要算进去

五、工程要点

  1. 全网同一个 T、同一个相位：CQF 的前提是 gPTP 时钟同步。各节点的周期必须对齐（相位差要纳入时延预算，不能靠运气）。
  2. T 的选取顺序：先统计"最坏周期到达字节量"→ 除以端口速率 → 得到 T 的下限；再叠加"大于最大帧时间"的约束；最后在此下限之上尽量取小以压低时延。
  3. 队列要成对，甚至成组：8 个出口队列可以组成 4 对，不同业务类别（如音视频、控制指令）各用一对，互不干扰。
  4. 必须配入队监管 / 队列长度管理：CQF 只承诺"能发出去的量"，装不下的部分必须有明确的处置策略（丢弃、降级、或提前在 PSFP 拦住），不能默默滚动——滚动就等于失信。
  5. "与流数无关"是有红线的：这个漂亮性质只在"每周期不超容量"成立时有效。流量工程没做，上界就是纸上的。
  6. 冗余路径必须对称：FRER 双路径的周期与相位一致，去重窗口才收得住。
  7. 帧长预算要算全：VLAN 标签、MACsec ICV、优先级标签都会让同一帧变长，直接吃掉"每周期能装几帧"。
  8. 验证看时间戳网格：出队时间戳应严格落在"周期边界"的网格上（同一批帧时间戳聚成一簇）；per-queue 的入队 / 出队 / 丢弃计数、以及"周期超容量"计数，是排查"周期到底有没有洗干净"的第一手证据。

六、三条铁律（记住这三句）

  1. 双缓冲 + 固定节拍：每个出端口准备成对的 两个队列，按 周期 T 奇偶交替当班；本周期到达的帧只写"等待席"，必须等到下一个周期才准转发 → 每跳停留 ≤ 2T。
  2. 上界 = (H+1)·T，且与流数量无关：时延只由 跳数 H 与 周期 T 决定；每过一跳只是把"出发周期号 +1"，所以 抖动不随跳数累积（前提：每周期不超容量）。
  3. T 是唯一的旋钮，也是唯一的事故源：T 必须 大于最大帧发送时间，且 每周期容量 ≥ 每周期到达量；否则帧滚到下一周期，上界立刻失效甚至丢帧——所以 CQF 必须配入口监管 / 丢帧策略，冗余路径的周期还要两侧对齐。

七、费曼简答题（用自己的话，不许用术语）

Q1：用"两个班次轮流值班"（或摩天轮、旋转寿司）打比方，讲清 CQF 的三条硬规则。为什么一帧到达后最多等两个周期就一定会被发走？为什么"本周期到达、本周期就发走"是不允许的？再想一想：为什么"每跳都往后推一个节拍"这件事，会让端到端的时延波动不会越走越大？（提示：误差不会累积，因为同一批帧被打包成一批一起走）

Q2：周期 T 为什么不能随便取值？请分别说清：T 太小时会发生哪两件坏事（一帧都发不完 / 本周期到达量装不下，余量滚到下一周期），T 太大时又要付出什么代价。为什么说 CQF 的时延上界"与网上有多少条流无关，却与跳数有关"？"不超容量"这个前提为什么必须靠入口监管来守，守不住会怎样？（提示：每周期容量 = 端口速率 × T；上界 = (H+1)T）

Q3（进阶）：CQF、Qbv、CBS 三者在"时延保证、配置成本、适用场景"上各有什么不同？为什么说 CQF"像 Qbv 的特化用法"（固定周期 + 两队列交替门控），却比 Qbv 好配置得多？CQF 的时延是"以周期 T 为颗粒被量化"的——这和 CBS 承诺的"平均速率"在语义上有什么区别？如果一个队列被超容量流量灌爆，CQF 会怎样"失信"？（提示：Qbv 要逐流算表、CQF 只要一个 T；CBS 管速率、CQF 管时延；滚动到下一周期 = 上界失效）
