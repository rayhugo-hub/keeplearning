一、先想想这个场景

4S 店工位上，诊断仪插上 OBD 口（车载以太网）。技师要读挂在 CAN 总线深处的 BMS（电池管理系统）的故障码——它没有以太网口，和诊断仪之间隔着一道中央网关：

flowchart LR T["🛠️ 诊断仪<br>（OBD 口，车载以太网）"] G["🚗 中央网关<br>（DoIP 网关）"] B["🔌 BMS<br>（只有 CAN 口）"] T -- "以太网 · TCP 13400" --> G G -- "CAN 总线" --> B

问题来了：诊断仪怎么知道网线上有车、是哪台车？怎么证明自己有资格发诊断？一条 UDS 指令又怎么穿过网关、变成 BMS 听得懂的 CAN 报文？

Lesson 39 讲过 DoIP 的"是什么/为什么"——UDS 搬上以太网、OTA 的高速公路。这一课是进阶：讲"怎么实现"——找车 → 激活路由 → 封装转发三道关卡背后的机制细节。

二、第一关：先"找到车"——车辆发现的三招

TCP 是一对一的：必须先知道对方的 IP，才能建立连接。可诊断仪插上线时，连"有没有车、车在哪个 IP"都不知道——所以第一步不能用 TCP，而是用 UDP 广播（端口 13400）"喊一嗓子"。

招数报文谁发给谁典型场景
① 广播点名0x0001 车辆识别请求诊断仪 → 全网（UDP 广播）4S 店：插上就问"谁在？"
② 精确呼叫带 VIN（0x0003）或带 EID（0x0002）的请求诊断仪 → 指定车（UDP）知道目标 VIN，从满场车里精确找
③ 守株待兔0x0004 车辆主动宣告车 → 全网（UDP 广播）车刚上电联网，主动广播"我在这"

（EID = 实体标识，和硬件强相关，相当于车的"设备指纹"。）

回应：被点到的网关/DoIP 节点回一条 0x0004 车辆识别响应，里面带着三件套：VIN（17 位车架号）、自己的逻辑地址、EID。

为什么回应里要带"逻辑地址"？ 一辆车上能对话的"实体"不止一个：中央网关、带 DoIP 的域控……各自有唯一的 16 位逻辑地址。诊断仪接下来建 TCP、做路由激活，认的都是这个逻辑地址——它是 DoIP 世界里的"门牌号"。

两个"为什么"：

  • 为什么找车用 UDP？ 广播是一对多，UDP 天然支持；报文小、丢了无所谓——再广播一次就行，不值得为它建连接、做重传。
  • 为什么宣告不"上电就喊"？ 车上一堆节点同时上电，如果同时广播会撞成风暴——所以要等一小段随机延时再宣告，错开高峰。

三、第二关："访客证"——路由激活，凭什么让你进门

找到了车、开了 TCP（还是端口 13400），能直接发诊断了吗？不能。想想看：如果任何插上网线的人都能给 BMS 发"擦除故障码""刷写"指令，那停车场里拔根线就能黑一辆车。

所以 TCP 连上后的第一件事是路由激活（Routing Activation）——相当于小区门口办访客证：

sequenceDiagram participant T as "诊断仪" participant G as "DoIP 网关" T->>G: ① TCP 连接建立（端口 13400） T->>G: ② 0x0005 路由激活请求（报上我的逻辑地址 0x0E00、激活类型） G-->>T: ③ 0x0006 激活响应（0x00 = 成功） Note over T,G: 网关把这条 TCP 连接和 0x0E00 绑定 Note over T,G: 此后这条连接 = 可信诊断通道 T->>G: ④ 0x8001 诊断消息（读 BMS 故障码） G-->>T: ⑤ 0x8002 收到回执，正在转发

激活时要声明两件事：

  1. 我的逻辑地址——诊断仪通常用 0x0E00（外部测试设备的约定地址，ISO 14229-1 附录）；网关校验"这个地址有没有资格、是不是冒牌货"。
  2. 激活类型——你想以什么身份进来：
激活类型含义典型场景
0x00 默认激活不做额外认证产线/售后基础诊断（具体策略 OEM 定）
0x01 WWH-OBD排放相关法规诊断年检、环保检测（只放开排放相关服务）
0x02 中央安全需要安全校验/证书OTA 刷写、解锁安全等级
0x80~0xFE OEM 自定义厂商自己定义各种特殊模式

响应码：0x00 = 成功；非 0 = 拒绝（比如"已经有一个激活的诊断仪了""安全校验不过""请求格式错"），具体原因码由 ISO 13400-2 定义。

激活成功后，网关内部发生了什么？——"绑定"。 网关在内部记下一行：这条 TCP 连接 ↔ 逻辑地址 0x0E00 ↔ 已激活。此后：

  • 这条连接上发来的 0x8001 诊断消息，网关才愿意解析、转发；
  • 别的连接想冒充 0x0E00？——查无此绑定，拒绝。
一句话：路由激活 = 网关给诊断仪发"访客证"，并把"人（逻辑地址）"和"门（TCP 连接）"绑在一起。 绑一次，整段诊断会话都有效，不用每条消息都验一次身——这就是 L39 说的"报名"背后的机制。

连接"假死"了怎么办？ 诊断仪可能死机、网线可能被踢掉，但 TCP 连接还半死不活地挂着。网关会发 0x0007 alive check（你还活着吗），诊断仪必须回 0x0008；不回？网关判定失效，回收路由——把访客证作废，把位置让给下一个诊断仪。这就是 DoIP 的"保活"。

四、诊断消息的"信封"——DoIP 报文长什么样

找车、激活、诊断……这些消息在网线上都穿着同一件"制服"：8 字节 DoIP 头 + 载荷。

字段长度作用
协议版本1 字节如 0x02/0x03（对应 ISO 13400-2 的不同年份版本）
版本反码1 字节版本号取反，接收方一眼识破"错乱/乱码"的头部
载荷类型 Payload Type2 字节这封信是什么（见下表）
载荷长度 Payload Length4 字节后面载荷有多少字节（不含头部）

常用载荷类型（ISO 13400-2）：

类型报文走什么协议干什么
0x0001 / 0x0002 / 0x0003车辆识别请求（普通 / 带 EID / 带 VIN）UDP找车
0x0004车辆识别响应 / 主动宣告UDP报上 VIN、逻辑地址
0x0005 / 0x0006路由激活请求 / 响应TCP办访客证
0x0007 / 0x0008alive check 请求 / 响应TCP保活
0x8001诊断消息TCP信封里装的才是 UDS 请求/响应
0x8002诊断消息正回执TCP网关说"收到，正在转发"
0x8003诊断消息负回执TCP网关说"我不收"，附原因码
0x0000通用头部 NACKTCP/UDP头部就不对（版本错、长度超限），直接拒

0x8001 诊断消息的载荷里装着什么？ 源逻辑地址（谁发的）+ 目标逻辑地址（发给谁）+ 一整条 UDS 报文。注意：UDS 报文是"原样"装进去的——DoIP 只换运输方式，不改"语言"。

"回执"为什么重要？ 这里有个容易混的点：

  • TCP 的确认：只保证"字节流到网关了"——网卡收了、内核收了，仅此而已；
  • 0x8002/0x8003 回执：是网关应用层的答复——"我拆开信封看了：目标地址认不认识？路由激活了没？报文超没超长？"

能转 → 0x8002；不能转 → 0x8003 并附原因码（如 0x02 目标地址未知、0x03 报文过大、0x05 目标不可达）。诊断仪不用干等 ECU 超时，立刻就知道"这封信送不出去、为什么"——这就是快速失败。

五、第三关：网关"翻译官"——从以太网到 CAN 总线

假设目标 BMS 挂在 CAN 上。网关收到 0x8001，拆开一看目标逻辑地址是 BMS，于是开始干翻译官的活。为什么不能"原样照搬"丢上 CAN？因为两边有三处不一样：

① 地址体系不一样 → 查路由表。 DoIP 世界认"逻辑地址"，CAN 世界认"诊断 CAN ID"。网关的路由表就是一张对照表：

目标逻辑地址通往哪条总线诊断 CAN ID说明
BMS（例 0x0719）CAN20x719（物理寻址）一对一，只发给 BMS
发动机 ECUCAN10x7E0一对一
整车（功能寻址）所有总线0x7DF（功能寻址）一对多广播，如"全体报告版本号"

② 报文长度不一样 → ISO-TP 分段。 CAN 一帧最多装 8 字节（CAN-FD 64 字节）。而一条 UDS 刷写数据动辄几百上千字节。所以要走 ISO-TP（ISO 15765-2） 拆包：单帧塞得下就直接发（≤7 字节）；塞不下就拆成 首帧（First Frame）→ 流控帧（Flow Control）→ 连续帧（Consecutive Frame） 一串发出去，BMS 收齐再拼回完整的 UDS 报文。反过来，BMS 的响应太长也要分段回来、网关重组后再装进 0x8001。

③ 语言不变。 翻译的是"路"，不是"话"：UDS 服务（0x22 读数据、0x2E 写数据、0x34/0x36 刷写……）从头到尾原样——BMS 执行的和诊断仪发的是同一条 UDS。

flowchart TB IN["以太网帧到达网关<br>（TCP 13400 上的 0x8001 诊断消息）"] P1["拆开 DoIP 信封：取出 UDS 请求 + 目标逻辑地址"] P2["查路由表：目标逻辑地址 → 哪条 CAN + 哪个诊断 ID"] P3["按 ISO-TP 拆段：单帧只装 8 字节<br>（首帧 → 流控帧 → 连续帧）"] OUT["从对应 CAN 口发出：<br>物理寻址（一对一）或功能寻址（广播）"] ECU["BMS 收齐分段 → 重组出完整 UDS → 执行"] IN --> P1 --> P2 --> P3 --> OUT --> ECU

为什么非要网关转一道？ 老一代 ECU 密密麻麻挂在 CAN 上、没有以太网口，不可能为诊断全部改造；网关做"翻译官"，一套 DoIP 入口就能服务全车所有总线——这也是中央网关在诊断架构里的核心价值。

六、把一条诊断请求的完整旅程串起来

诊断仪读 BMS 故障码（UDS 0x19 读故障码）的全程：

sequenceDiagram participant T as "🛠️ 诊断仪" participant G as "🚗 中央网关（DoIP 网关）" participant B as "🔌 BMS（挂在 CAN2）" Note over T,G: 找车：UDP 广播 0x0001 → 网关回 0x0004（VIN + 逻辑地址） Note over T,G: 建 TCP（13400）→ 0x0005 路由激活 → 0x0006 成功，绑定 T->>G: 0x8001 诊断消息（源 0x0E00 → 目标 BMS，UDS 0x19） G-->>T: 0x8002 正回执（收下了，正在转发） G->>B: 查路由表 → CAN2 发 0x719：UDS 0x19（ISO-TP 分段） B-->>G: 分段响应 → 网关重组 G->>T: 0x8001 诊断响应（UDS 0x19 的应答，装回 DoIP 信封）
  1. 找车：诊断仪 UDP 广播 0x0001，网关回 0x0004，报上 VIN 和逻辑地址；
  2. 开门：诊断仪向网关的 IP:13400 建 TCP，发 0x0005 路由激活，网关回 0x0006 成功，并把连接和逻辑地址绑定；
  3. 送信：0x8001 诊断消息上路，网关先回 0x8002"收到"，再查路由表翻译；
  4. 翻译：逻辑地址 → CAN 诊断 ID，长报文按 ISO-TP 拆段送上 CAN2；
  5. 返回：BMS 的响应分段回来，网关重组、装进 0x8001，原路送回诊断仪。

七、诊断流量在车载网络里的"地位"

把 L47 以来的"车载以太网深度系列"串一遍：TSN（L47）让关键帧准点 → PHY（L48）把帧变成电信号 → 交换机（L49）分流隔离 → FRER（L50）让关键帧断一条路也不丢。诊断/OTA 流量在队列里排哪？——尽力而为：

流量可靠性怎么保证开 FRER？
转向/制动控制指令发送端双发（FRER）+ TSN 调度✅ 开
摄像头视频流丢帧可容忍、可恢复❌ 不开
诊断 / OTA 刷写TCP 重传兜底 + UDS 超时重试❌ 不开
  • 诊断不需要 FRER：它走 TCP，丢了会重传；UDS 层还有超时重试（比如 0x36 传输数据可以断点续传）。给诊断开 FRER 纯属浪费带宽。
  • 但诊断可能"欺负"关键流：OTA 一刷写就是几十 MB 连续数据。如果它和转向指令抢同一个出口队列，转向就得排队——所以要用 L49 的流分类/VLAN 把诊断、OTA 关进低优先级队列，必要时还要限速监管（TSN 家族里的 802.1Qci / PSFP 每流监管就是干这个的，后续课程会深入）。
  • 和 L39 呼应：OTA 的下载段走 HTTPS 到 TBOX，刷写段由 TBOX 当"内部诊断仪"，用 DoIP 把固件喂给各 ECU——DoIP 是 OTA 落地的最后几公里。

八、三条铁律（记住这三句）

  1. 先找车、再敲门、后送信——UDP 找车（0x0001/0x0004）→ TCP 上路由激活（0x0005/0x0006）拿"访客证"→ 绑定后的连接才能发 0x8001 诊断消息。少一步都进不了门。
  2. UDP 负责"问"，TCP 负责"送"——找车是一对多广播，丢了再问一次；诊断消息要按序不丢，必须走 TCP；网关回 0x8002/0x8003 是应用层回执（告诉你能不能转），和 TCP 的字节确认是两回事。
  3. 网关是翻译官，不是快递员——UDS 是"语言"，原样不变；要翻译的是"路"：逻辑地址 → CAN 诊断 ID、长报文 → ISO-TP 分段、一对一物理寻址 → 一对多功能寻址。没有路由表，诊断仪连 BMS 的门都找不到。

Q1：用"去陌生小区找朋友"打比方，讲一讲：为什么诊断仪不能一插上网线就直接发诊断指令？"路由激活"相当于进门前的什么手续？为什么办好一次之后，后面反复进出就不用再办了？（提示：激活后网关把什么和什么"绑"在了一起？）
