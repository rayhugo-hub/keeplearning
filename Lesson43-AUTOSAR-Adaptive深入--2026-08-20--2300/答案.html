费曼简答题参考答案

Q1：Classic 排期半年 vs Adaptive 动态——本质区别

类比技术含义
Classic = 老式交换机，端口跳线接死RTE + 静态配置在编译期定死：谁调用谁、信号矩阵、调度表全部固定。加功能 = 改配置 → 重编译 → 重集成 → 重新刷写 → 关联 ECU 联动 → 排期半年
Adaptive = 手机 App，动态寻址、按需连接服务运行期发现与绑定：加功能 = 新增/升级一个服务进程，客户端动态找到它，只更新一个进程
本质区别：静态绑定 vs 动态绑定。Classic 不是"落后"，是确定性优先（刹车/气囊要可证明）；Adaptive 基于 POSIX OS，有进程隔离，一个服务崩了不拖垮整车。

Q2：Event / Method / Field 适用场景 + "车速上报"归属

交互本质适合场景
Event服务端主动推送（订阅制）周期性/变化触发的数据流：车速、温度、电量、路况
Method客户端请求-应答一次性功能调用：规划路线、开关功能
Field读写属性（可带通知）设置/读取状态项：开关、模式、标定量
"车速上报"属于 Event（订阅）：车速是周期性数据流（10/100ms 一报），多端（仪表、ADAS、能量管理）都要用，订阅制天然一对多；客户端订阅后持续接收，符合"发布-订阅、持续推送"模型。若只需"现在瞬时车速多少"一次性回答，才是 Method。

Q3：TTL（生存时间）的作用

  • 服务端每次 OfferService 带 TTL（如 3s），并周期性重发续约；TTL 到期没续约 → 判定该实例下线，停止发请求、触发重新发现
  • 没有 TTL：客户端无法区分"暂时没回包"和"服务已经没了"，会一直向僵尸服务发请求直到超时
  • 只能靠自身请求超时猜测，不可靠、反应慢——又退回静态世界
加分：续约周期应远小于 TTL（如 TTL=3s、1s 续约一次），留足网络抖动余量。这是分布式系统"心跳 + 租约（lease）"的经典模式。

选择题参考答案

MCQ1：Adaptive 平台主要运行在哪种硬件上？

✅ C. 座舱域控制器 / 中央计算 HPC
解析：Adaptive 需要 POSIX OS、进程隔离、高算力——座舱/智驾/HPC；气囊、车窗电机、雨刮继电器都是资源受限的 Classic 场景。

MCQ2：持续接收周期性"电池电量"推送，用哪种交互？

✅ B. Event（事件，订阅）
解析：持续、周期、推送 → 发布-订阅的 Event；Method 是一次性请求-应答，Field 是读写属性。

MCQ3：服务端启动后如何让客户端"找到"自己？

✅ A. 广播 OfferService（含实例 ID、端点、TTL）
解析：OfferService 是服务端"挂牌广播"；客户端用 FindService 找、SubscribeEvent 订阅；"写死地址"是静态世界的反面教材。
