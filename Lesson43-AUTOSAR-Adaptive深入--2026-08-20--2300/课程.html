一、先想想这个场景

车上的新功能（比如"记忆泊车"）从提出到上线，动辄排期 6 个月——因为要给每个相关 ECU 重新刷软件、重新做集成测试。而手机上的 App 加个功能，今天更新、明天就能用。差距在哪？

Lesson 41 讲了 SOA 与中央计算：把整车功能拆成"服务"。但服务之间怎么通信？怎么找到对方？谁来管服务的启动与停止？——这就是 AUTOSAR Adaptive 平台的三大机制：

  1. S2S（ARA::COM）——服务之间怎么"对话"？（通信）
  2. 服务发现（SOME/IP-SD）——客户端怎么"找到"服务？（发现）
  3. 执行管理（Execution Management）——服务进程"跑不跑、挂了怎么办"？（生命周期）
这一课讲清楚：Adaptive 平台 = 给汽车软件装上一个"运行时"——服务动态发现、动态调用、动态启停。Classic 是"出厂焊死"，Adaptive 是"运行时装拆"。

二、Classic 还是 Adaptive？一张表看懂

维度AUTOSAR ClassicAUTOSAR Adaptive
定位硬实时、资源受限的 ECU（刹车、气囊）高算力、高带宽的域控制器 / HPC（座舱、智驾、中央计算）
运行模型静态：通信、调度编译期定死（RTE + 静态配置）动态：服务运行期发现与绑定（ARA + 动态启动）
操作系统OSEK/FreeRTOS 类，无 MMU 或轻量POSIX（Linux/QNX）——有进程、有文件系统
通信方式RTE 函数调用 / 信号（信号矩阵定死）S2S 服务化通信（SOME/IP、DDS）
更新整包刷写（FOTA 整镜像）进程级更新（可只更新一个服务）
类比老式交换机：端口跳线接死互联网：动态寻址 + 按需连接
一句话：Classic 管"确定性"，Adaptive 管"灵活性"。新架构里两者共存——安全关键功能留在 Classic，需要进化的功能放到 Adaptive。

三、S2S（ARA::COM）：服务怎么"对话"？

三种交互方式（记住这个框架）

交互模式类比典型场景
Event（事件）服务端发布，客户端订阅，持续推送关注公众号，更新就推送车速、路况、电池状态上报
Method（方法）客户端请求，服务端应答（同步/异步）打电话问一句，等回答请求路线规划、开关功能
Field（字段）读写一个属性，可带通知查看/修改设置项读取/设置"自动泊车开关"

绑定（Binding）：SOME/IP（跨 ECU 走以太网）、IPC（同处理器进程间）、DDS（智驾以数据为中心）

sequenceDiagram participant C as 客户端(Client) participant S as 服务端(Server) C->>S: Method 请求(带参数) S-->>C: Method 应答(带结果) S-->>C: Event 推送(周期/变化触发) C->>S: Field 读/写
一句话：Event 是"订阅推送"，Method 是"请求应答"，Field 是"读写属性"——记住这三样，S2S 就懂了一半。

四、服务发现（SOME/IP-SD）：怎么"找到"服务？

消息方向含义
OfferService服务端 → 网络"我上线了，在这（IP:端口:实例ID）"
FindService客户端 → 网络"谁提供 XX 服务？"
SubscribeEvent客户端 → 服务端"我订阅 XX 事件"
SubscribeEventAck服务端 → 客户端"订阅成功"
sequenceDiagram participant C as 客户端 participant N as 服务发现(SD) participant S as 服务端 C->>N: FindService S->>N: OfferService(实例ID,端点,TTL) N-->>C: 收到Offer C->>S: SubscribeEvent S-->>C: SubscribeEventAck S-->>C: Event数据推送 S->>N: OfferService(TTL续约)
一句话：服务发现 = 服务端"开店挂牌"（Offer），客户端"上门找店"（Find），订好"会员"（Subscribe），老板定期"续牌"（TTL）。

五、执行管理（Execution Management）：服务进程"跑不跑、挂了怎么办"？

stateDiagram-v2 [*] --> Running: 启动 Running --> Ready: 暂停/待命 Ready --> Running: 恢复 Running --> Terminating: 停止请求 Terminating --> [*]: 退出 Running --> [*]: 崩溃
  • Machine State / Function Group（功能组）：按整车状态（驻车/行驶）开关功能组——省算力、降功耗、减少攻击面
  • 故障管理（Watchdog / 重启策略）：服务崩溃 → EM 拉起；反复崩溃 → 限次重启 + 上报故障。支撑功能可用性
一句话：EM 是汽车软件的"进程管家"——管启动、管待命、管退出、管重启。

六、三条铁律（记住这三句）

  1. Adaptive = 把车机软件从"跳线接死"改成"App 化"：服务动态发现、动态调用，升级只动一个进程。
  2. S2S 三种交互：Event 订阅推送、Method 请求应答、Field 读写属性——先判断交互类型，再谈通信细节。
  3. EM 管生命周期：Running/Ready/Terminating/崩溃重启，功能组按整车状态开关——可用性靠它兜底。
