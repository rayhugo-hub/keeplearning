Lesson 17 — 答案

中央计算平台（HPC）——区域架构的"超级大脑" — 参考答案

费曼简答题参考答案

Q1（HPC 和普通电脑有什么区别？）

参考答案方向（"普通台式机 vs 坦克里的加固电脑"类比）：

普通电脑（台式机）：放在 25°C 空调房里，从不震动，死机重启，用 3 年就换。

HPC（车规）：

  1. 温度：夏天车内暴晒 85°C，冬天 -40°C——普通芯片会失效。HPC 必须满足 -40°C ~ 125°C 车规范围（AEC-Q100 认证）
  2. 振动：普通硬盘在颠簸路面上一小时就坏。HPC 通过 10 年 20 万公里 振动耐久测试——无风扇、无机械硬盘，全固态
  3. 安全：电脑蓝屏重启就行。HPC 死机→刹车可能失效！必须通过 ISO 26262 ASIL 功能安全认证，关键功能有硬件冗余
  4. 寿命：消费电子 2~3 年，汽车要求 10~15 年 不间断运行

一句话：你把台式机扔后备箱去越野——一小时就坏。HPC 是专为"残酷环境 + 生命安全"设计的加固版超级电脑。

Q2（为什么要虚拟化？什么是 Hypervisor？）

参考答案方向：

为什么需要两个系统？座舱需要丰富生态和漂亮 UI → Android 最合适，但非实时；安全系统需要微秒响应、零死机 → RTOS/AUTOSAR，但不能跑 App。

为什么不能只是两个程序？跑同一个 OS 里→一个崩溃另一个也完蛋，或者一个占满 CPU 饿死另一个。车上等于杀人。

虚拟化（Hypervisor）——"一屋分三房"：Hypervisor 直接运行在硬件之上，把一颗物理芯片虚拟成多个完全独立的虚拟机：VM1 跑 Android（座舱），VM2 跑 Linux（智驾），VM3 跑 RTOS（安全）。三个虚拟机完全隔离——VM1 崩溃了不影响 VM2/VM3。Hypervisor 保证每个虚拟机有专属 CPU 核和固定内存，谁也抢不了谁的资源。

Q3（"调 23°C + 降车窗"的完整指令旅程）

参考答案方向：

  1. 语音输入：麦克风拾音 → HPC 的 NPU 上跑语音 AI 模型 → 转成文字
  2. 意图理解：座舱 Android 的 NLP 解析出两个独立命令——"空调设 23°C"和"左前车窗降一半"
  3. 服务调用：Android App 将每个意图转为 SOME/IP 调用——空调服务的 setTemperature(23) + 车窗服务的 setWindow(左前, 50%)
  4. 以太网传输：HPC 的以太网 Switch 通过千兆车载以太网广播两个 SOME/IP 请求
  5. ZCU 执行：空调请求→前部 ZCU 控制压缩机/膨胀阀；车窗请求→左前 ZCU 输出 PWM 驱动电机→玻璃降一半
  6. 状态上报：两个 ZCU 通过 SOME/IP Event 上报执行结果
  7. UI 更新：HPC 座舱系统更新界面——空调显示 23°C ✓，车窗显示半开 ✓

选择题答案

题号答案解析
1 B HPC 是"大脑"——处理融合感知、全局决策、AI 推理；ZCU 是"手脚"——就近采集传感器信号、驱动电机/灯/锁等执行器、转发数据。A❌ 分工反了；C❌ 功能完全不同，不是位置差异；D❌ 完全反了——导航娱乐在 HPC 上，车窗控制由 ZCU 负责。
2 B Hypervisor 的核心价值是隔离——让多个不同实时性/安全等级的操作系统互不干扰地运行在同一颗芯片上。座舱用 Android（功能丰富但非实时），智驾用 Linux（可靠），安全用 RTOS/AUTOSAR（微秒级实时、ASIL-D）——三者通过 Hypervisor 隔离。A❌ 虚拟化通常有少量性能开销；C❌ 无关；D❌ 恰恰相反——正是不能跑在一个系统里才需要虚拟化。
3 B SOME/IP 是 AUTOSAR 标准的面向服务协议（request/response/event 模式），适合按需调用的服务：关窗、调空调、导航询问——像"你帮我订个外卖"（一次请求→响应）。DDS 是数据分发协议（publish/subscribe），适合持续广播的数据流：传感器数据、车辆状态——像"你订了天气预报，每天自动推送"（谁需要谁订阅，持续推送）。A❌ 正好说反了；C❌ 完全不同；D❌ 两者都是车载骨干协议。
